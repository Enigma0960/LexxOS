# Правила структуры C++-кода LexxOS

Документ устанавливает обязательные правила для нового кода и текущего структурного рефакторинга LexxOS.

## Классы

Каждый именованный класс, являющийся контрактом подсистемы, backend-классом, device/app implementation, RAII guard или
переиспользуемой моделью, размещается в отдельной паре файлов:

```text
class_name.h
class_name.cpp
```

В заголовочном файле находятся объявление класса, объявления методов, поля, необходимые forward declarations и
минимальный набор include-файлов. В исходном файле находятся реализации нетривиальных методов, закрытые вспомогательные
функции, локальные константы и таблицы, не являющиеся частью публичного API.

В одном заголовке не объявляются несколько самостоятельных классов. Правило также распространяется на классы команд,
backend-классы и RAII guards.

Implementation-local классы в `.cpp` допустимы только как private detail одного translation unit: небольшие test doubles,
platform bridge objects или callback helpers, которые не являются API и не нужны другим файлам. Если такой класс растёт,
получает самостоятельную ответственность, требует независимых tests или начинает использоваться повторно, он переносится
в собственную пару файлов в каталоге `detail`.

## Структуры

Связанные структуры разрешается группировать по предметной области:

```text
shell_types.h
vfs_types.h
storage_test_types.h
gameboy_runtime_types.h
```

Публичные структуры размещаются рядом с публичным API. Внутренние структуры, которые являются контрактом между `.cpp`
файлами, размещаются в тематическом заголовке `module/detail/module_types.h`.

Implementation-local структуры в `.cpp` разрешены для короткоживущих row/config/parser/callback contexts, если они
используются только внутри одного файла и делают код проще. Если отдельная структура не улучшает читаемость, следует
передать данные явными параметрами.

## Реализация в заголовках

Нетривиальная реализация методов классов размещается в `.cpp`.

В заголовках могут оставаться простые `constexpr` getters, шаблонные функции, compile-time helpers и значения
`static constexpr`. Исключение должно быть обусловлено требованиями компиляции, а не удобством размещения кода.

## Размер модулей

Ориентиры:

- обычный `.cpp`: до 400–600 строк;
- связный алгоритмический модуль: до 800–1000 строк;
- заголовок класса: обычно до 200–250 строк.

Размер не является самостоятельной целью. Файл разделяется по ответственности, а не механически по числу строк.

Один модуль не должен одновременно реализовывать команды, модель данных, интерфейс пользователя, драйвер и тестовую
инфраструктуру.

## Большие функции

Большая последовательная функция разделяется на визуальные блоки короткими комментариями:

```cpp
int SdSpeedScanProgram::run(...) {
    // Проверка аргументов и построение конфигурации.
    ...

    // Подготовка карты и эталонных данных.
    ...

    // Выполнение тестовых проходов.
    ...

    // Восстановление настроек и очистка ресурсов.
    ...
}
```

Комментарий должен описывать цель следующего блока, быть коротким и предметным, отделяться пустой строкой, не повторять
отдельную строку кода и быть написан на русском языке.

Комментарии не заменяют декомпозицию. Блок следует вынести в отдельную функцию или класс, если он используется повторно,
имеет самостоятельные входные данные и результат, содержит отдельную обработку ошибок, может тестироваться независимо
или занимает значительную часть функции.

Функции длиннее 50–70 строк должны иметь явную структуру или быть декомпозированы. Функции длиннее 120–150 строк обычно
требуют выделения подфункций. Исключениями могут быть линейные таблицы и проверенные производительные hot paths.

## Язык

Документация и поясняющие комментарии пишутся на русском языке. Имена API, команд, файлов, протоколов и технические
термины сохраняются без искусственного перевода, если это улучшает точность.

## Форматирование

Механическое форматирование C/C++-кода задаётся файлом `.clang-format` в корне репозитория. Перед релизной меткой
проверяются только собственные исходники проекта; сторонние зависимости, build-каталоги и generated artifacts не
форматируются.

Проверка без записи:

```bash
git ls-files -z '*.cpp' '*.h' '*.hpp' '*.c' '*.cc' '*.cxx' \
  ':!:third_party/**' ':!:build/**' ':!:cmake-build-*' \
  | xargs -0 clang-format --dry-run --Werror
```

Если `clang-format` не находится в `PATH`, в команде используется абсолютный путь к установленному бинарю.

Массовое форматирование должно идти отдельным механическим патчем без поведенческих изменений. Если форматтер делает
большую таблицу менее читаемой, допустимо явно защитить таблицу `clang-format off/on` и оставить рядом короткое
обоснование.

## Безопасность рефакторинга

Структурный патч не должен одновременно менять поведение.

При перемещении кода сохраняются имена и порядок регистрации команд, аргументы, коды возврата, форматы диагностического
вывода, feature flags, ограничения памяти и platform-specific поведение.

После каждого патча выполняются доступные host, simulator и hardware-oriented проверки затронутой подсистемы.

## Удаление устаревшего кода

Перед удалением проверяются все CMake source lists, include/call sites, tests и metadata
генератора документации. Отсутствие файла в одном preset не означает, что он не используется.
Копии команд, уже заменённые общим модулем, удаляются вместе с их private helpers,
если у helpers не осталось потребителей. Полезная документация переносится к актуальной реализации.

Общая регистрация команд и общий список исходников имеют один источник. Платформенные
ветки добавляют backend и hardware extensions, а не копируют весь список команд.
Экспериментальный статус и compatibility alias сами по себе не являются основанием для удаления.

## Чувствительные аргументы команд

Для пароля, токена или другого секрета в `ProgramArgumentSpec` задавайте `.sensitive = true`.
Shell исключает весь вызов такой команды из истории до разбора аргументов, включая ошибочные вызовы.
Политика консервативна: упоминание имени чувствительной команды отдельным токеном тоже исключает строку
(например, `echo wifi-connect`). Старые Wi-Fi-записи фильтруются даже в сборках без Wi-Fi-команд.
Это политика истории, а не маскирование терминального ввода или шифрование конфигурации.
