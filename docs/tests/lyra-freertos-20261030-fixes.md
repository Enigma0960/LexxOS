# Lyra / FreeRTOS: исправления после переполнения bench

> **Исторический протокол RK3506.** Последующие команды и ограничения
> отражают конкретный ранний этап и сохранены для воспроизводимости,
> а не как инструкция текущего профиля. На 04.11.2026 на Lyra работают FreeRTOS CPU0, managed MMU,
> LCD/SD RX PL330 DMA и опциональный SD1 FAT RW.
> [Актуальное состояние](../boards/picocalc_lyra_m.md#аппаратные-результаты).

Результаты получены 30 октября 2026 г.

## Подтверждённое наблюдение

`bench` дошёл до `native-before` и завершился
`panic: FreeRTOS stack overflow in task bench`. Размер стека был 5120 байт.
До этого SD сообщила `probe failed`, клавиатура — `initialize-keyboard-state-read`.
LCD использовал намеренно ограниченный PIO-профиль.

## Исправления

- Общий `LEXXOS_KERNEL_FREERTOS` теперь установлен вместе с платформенным макросом:
  kernel name и stack watermarks больше не отключены препроцессором.
- Стек bench увеличен до 16 КиБ. GCC генерирует `.su` для аудита кадров.
  В этой debug-сборке собственный кадр `BenchmarkProgram::run` — 1920 байт,
  `sampleBenchmarkNative` — 1592 байта. Эти числа не включают всю цепочку вызовов
  и контекст переключения; они не заменяют измерение watermark.
- Реестр задач защищён от вытеснения при выделении/освобождении и копировании
  snapshots. Visitor вызывается после снятия защиты, может выводить текст/yield.
  Размеры стека округляются вверх до элементов StackType_t.
- UART task writes используют mutex; bench TSV row и диагностическое сообщение
  клавиатуры формируются целиком. IRQ/ранний boot не блокируются на task mutex.
  Это не полноценная перерисовка shell prompt при асинхронных сообщениях.
- Готовность клавиатуры больше не подменяется готовностью I²C-контроллера.
  Input task продолжает вызывать pollEvent для восстановления неготового устройства.
- Аппаратный I²C сохраняет первую ошибку до STOP cleanup: NACK/timeout,
  ожидаемый event и IPD. event: START=0x10, TX=0x4, RX=0x8, STOP=0x20.
- Boot SD failure и `sd-media status` выводят protocol stage и response (response в десятичном виде; 255 означает 0xff).
  Добавлена `sd-media probe`, запрещённая при смонтированной карте.
- Автоматическое сохранение отчёта на недоступное/RO хранилище теперь даёт
  skipped и консольный отчёт, а не ошибку всего теста. Явный `--out` остаётся строгим.

## Повторный прогон: Data Abort при загрузке

Следующая проверка пользователем обнаружила регрессию после включения общего
`LEXXOS_KERNEL_FREERTOS`: после `FreeRTOS: mounting PicoCalc sd1...` CPU остановился:

```text
ARM exception 4 at PC=0x02013360 SPSR=0x6000001F DFSR=0x00001008 DFAR=0x0211D630; halted
```

В ELF проверенного образа (kernel payload 1175932 байта) адрес PC соответствует
`LDREXB` в `std::atomic<bool>::exchange`. DFAR расположен в массиве FAT volumes;
новый RTOS-путь `FatVolume::lockOperation` использовал atomic exchange для ленивого
создания mutex. Таким образом, это аварийная остановка при подготовке FAT, а не
зависание LCD. Текущий RK3506 bootstrap работает с выключенным MMU.

Создание FAT mutex переведено на `ensureRecursiveMutex`: короткие критические
секции FreeRTOS защищают чтение/публикацию указателя, выделение памяти и удаление
проигравшего кандидата выполняются вне секций. Тест моделирует конкурирующую
публикацию, повторное обращение и отказ выделения памяти.

В benchmark также устранён `fetch_add` общего счётчика: каждый worker публикует
собственный флаг завершения, управляющая задача ждёт все созданные workers.
В пересобранном ELF в прикладных функциях этих exclusive-инструкций больше нет.
Они остаются в библиотечных обработчиках C++ exceptions/handler setters; это
ограничение текущего bootstrap, а не подтверждение общей поддержки atomics.

Новый FreeRTOS kernel payload — 1175012 байт. Обе ARM-сборки упакованы успешно.
После исправления прошли 119/119 CTest, Markdown, C++ layout и `git diff --check`.
Host quick benchmark доходит до summary; отсутствующие устройства дают ожидаемые
ошибки и skipped, это не аппаратный PASS.
Повторный запуск на плате ещё не выполнен: сначала требуется проверить появление
shell prompt, затем запускать `bench --profile quick --no-save --no-display`.

## Следующий срез: I2C recovery и вывод отчёта

После quick-прогона исправлены две программные причины задержек/отказов:

- Rk3506I2cBus опрашивает IPD до проверки wall-clock deadline. Уже завершённая
  аппаратная фаза не считается timeout после вытеснения задачи; START/TX/RX/STOP
  имеют отдельный бюджет 20 мс.
- После настоящего timeout следующая транзакция вызывает recovery callback.
  Платформа временно переводит только I2C2 pins в GPIO open drain, вызывает
  SoftwareI2cBus::clearBus (до 9 импульсов SCL + STOP, bounded clock stretching),
  затем восстанавливает RMIO/pinmux и сбрасывает только I2C2. Драйвер возвращает
  CLKDIV. Никаких адресных/регистровых команд slave при clear не отправляется.
  Обычный NACK при успешном STOP recovery не запускает. При неудаче новая
  транзакция не начинается, исходная ошибка сохраняется; следующая попытка
  повторяет recovery. Диагностика добавляет `recovery=successes/attempts`.
- UART normalization собирает короткую запись вместе с CR/LF в один platform
  write. Длинный поток передаётся ограниченными чанками без потери данных.
  Это устраняет конкретное дробление TSV-строк, но не обещает атомарность
  произвольной последовательности отдельных write или shell prompt redraw.
- На Lyra/FreeRTOS mirror/presenter имеют priority 1, как input/bench;
  console остаётся priority 2. Существующие ожидания framebuffer освобождают CPU
  через sleepMs. Отрисовка PIO получает CPU по time slicing, вместо вытеснения
  input/bench на весь кадр. Скорость и отзывчивость нужно сравнить на плате.
- `bench --no-mirror` вместе с `--no-display` позволяет измерить UART-прогон
  без текстового mirror. Summary показывает отдельно phase-work/report-output.

Сначала сравнить эти команды (raw SD test только читает):

```text
bench --profile quick --device sd1 --no-save --no-display --no-mirror
bench --profile quick --device sd1 --no-save --no-display
```

Нужны summary обоих запусков, минимальные task-free и строки I2C recovery.
Если аппаратный START продолжает зависать после успешного recovery, потребуется
дальнейшая проверка SCL/SDA/таймингов. Этот срез ещё не проверен на устройстве.

Локальная проверка этого среза: 119/119 CTest; обе ARM-конфигурации собраны
и FIT упакован. Новый FreeRTOS payload — 1183812 байт. Host quick/no-mirror
доходит до summary, неверное сочетание без no-display отклоняется. Тест также
проверяет, что повторное применение focus mode не снимает вложенную suspension.
Прошли Markdown, C++ layout затронутых каталогов и `git diff --check`.

### Следующие изменения для задержки LCD

- У Lyra/FreeRTOS software-scroll repaint ограничен четырьмя строками на кадр.
  Пока repaint не закончен, терминальный снимок остаётся стабильным. Это
  прогрессивное обновление полосами; весь viewport больше не публикуется атомарно.
- Если накопилось больше двух обычных порций текста, парсер разбирает до 4096
  символов перед очередной перерисовкой; история сохраняется, промежуточные
  экранные кадры для каждой порции отчёта не строятся.
- Исправлен обход dirty rows: старт scan фиксируется на весь проход, чтобы
  изменение следующего scan row не пропускало ещё грязные строки.
- Неудачный I2C recovery повторяется не чаще раза в 250 мс. Retry loop до истечения
  паузы возвращает отказ без GPIO/сброса и сохраняет исходную диагностику.
- На границе timeout I2C повторно проверяет IPD перед отказом. Диагностика хранит
  проверенное значение pending, а не более поздний снимок с уже прибывшим completion.
- Native report добавляет lcd-frame draw/copy/queue/present ticks и lcd-console
  queued/processed chars, flushes и drawn rows для измерения оставшейся задержки.

Для проверки отображения использовать обычный mirror (quick — профиль по умолчанию):

```text
bench --device sd1 --no-save --no-display
```

`--no-display` пропускает активные графические тесты, но оставляет текст на LCD.
`--no-mirror` добавлять только для сравнительного UART-прогона. Новые изменения
ещё не прошли аппаратную проверку.

Локально для изменений задержки LCD прошли 119/119 CTest, обе ARM-сборки

## Наблюдение 18:16: I2C улучшился, текст LCD задерживается до clear

По фотографиям и описанию пользователя: клавиатура начала реагировать, постоянных
I2C ошибок больше не видно; обновляются время и заряд. После запуска bench на LCD
остаётся команда/загрузочный текст. `clear`, введённый с клавиатуры устройства,
примерно через 5 секунд очищает экран, после чего время выглядит отзывчивым.
Это подтверждает улучшение ввода по наблюдению пользователя, но не длительный
I2C stress или точную частоту обновления LCD.

В коде обнаружен обход ограниченного flush: shell/focus вызывали `refresh()`,
который из вызывающей задачи синхронно дорисовывал все строки software scroll.
Оптимизация Debug LCD hot path также охватывала SPI/pixel transport, но не
терминал, screen buffer, шрифты и console renderer.

Для Lyra/FreeRTOS внесены изменения:

- `refresh` и `clear` публикуют запросы, выполняемые в очередном mirror flush.
  Clear сбрасывает старую очередь сразу, но сохраняет новый prompt после запроса;
  при конфликте display resource запрос повторяется после освобождения ресурса.
- Повторная установка уже активного Text/Graphics mode стала no-op: focus больше
  не помечает всё окно грязным без фактического изменения режима.
- Разбор очереди прерывается после 4 мс wall time, даже если увеличенный лимит
  символов ещё не исчерпан. Строки публикуются до опустошения backlog.
- Terminal/font/screen/console rendering включены в существующую опцию
  LEXXOS_RK3506_LCD_OPTIMIZED (-O2 в Debug).
- В отчёте lcd-console появились max-parse/max-flush (мс с последнего сброса
  статистики, включая вытеснение). Это измерения, не гарантия жёсткого real-time.

Новый тест собирает настоящий renderer с DeviceManager, fake panel/clock и
критическими секциями FreeRTOS. Проверяет кадр при непустой очереди, обновление
status bar до её опустошения, асинхронный refresh, clear при занятом ресурсе,
сохранение prompt и отсутствие полного repaint при повторном focus mode.

Новый FreeRTOS kernel payload — 1156652 байта. Аппаратная перепроверка этих
изменений остаётся открытой; фотографии относятся к предыдущему образу.

## Прогон 18:27 и переход к снимкам страницы

Пользовательский лог для payload 1156652 байта:

- quick с SD1 завершился: 9 фаз, 0 failures, 48 skipped/unavailable строк,
  summary elapsed 32157 мс, phase-work 14817 мс, report-output 13344 мс.
- Секторное чтение SD ok, 8 KiB/s в данном прогоне; это не сравнение чистой SPI скорости.
- Между native snapshots очередь LCD выросла 1869 → 19324 символа, а processed
  вырос только 780 → 1725. Presented frames: 31 → 81. То есть накопился backlog,
  хотя сам тест уже закончился. Ощущение циклического движения текста совпало
  с повторной полосной перерисовкой и медленным разбором очереди.

Пользователь выбрал поведение «последние строки сразу, без анимации». Новая модель:

1. Терминал добавляет данные в логическое кольцо строк и ограниченную историю.
   Newline не копирует всю таблицу символов/атрибутов и не запускает анимацию.
2. Renderer разбирает порцию очереди независимо от прошлого repaint и строит
   целую актуальную видимую страницу в back buffer. Промежуточные положения
   software-scroll не публикуются полосами.
3. Ручная навигация перемещает viewport истории. Новый вывод не возвращает
   вручную выбранную страницу к tail; возврат выполняется существующими клавишами.
4. Мягкий parse deadline проверяется после минимум 1024 символов (далее каждые
   64), иначе вытеснение на SPI presenter могло завершать порцию после 1 символа.
5. DoubleBufferedDisplay предпочитает RGB565 stream; renderer не выполняет
   RGB565 → RGB888 → RGB565 перед заполнением framebuffer. Это независимый
   контракт входа; wire format панели остаётся прежним.

Последующие тесты сравнивают конечные пиксели порционного и цельного снимка,
проверяют порядок строк/цветовых атрибутов после множества оборотов кольца,
историю и ручную навигацию. Предыдущие полосные эксперименты выше оставлены
как история диагностики, они не описывают текущую модель вывода.

Аппаратная скорость новой модели пока не измерена. Сравнивать следует не только
summary elapsed, но и разницу queued-chars/processed-chars и отзывчивость часов.

Markdown, C++ layout и `git diff --check` прошли. FreeRTOS payload — 1156708 байт,
SHA-256 `9b6033260efe28195a765af80c667862130cd05e011a03af0a14943c1c59e61c`.
