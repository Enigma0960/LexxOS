# PicoCalc / Luckfox Lyra M (RK3506G2)

Единое руководство по плате Lyra M и её подключению к PicoCalc.
Рабочая реализация использует CPU0 Cortex-A7, FreeRTOS,
управляемую MMU с D-cache, DMA дисплея и чтения SD, FAT RW на съёмной карте.
Linux для выполнения LexxOS не требуется.

Lyra входит в план выпуска 0.1.1. Работа съёмной SD, клавиатуры, LCD и строки
состояния подтверждена в [ручной проверке автора](#аппаратные-результаты).
Вывод звука на Lyra пока недоступен.

## Плата и подключение

Luckfox Lyra M: Rockchip RK3506G2, ARMv7-A Cortex-A7, 128 МиБ DDR3, без NAND.
LexxOS использует CPU0; SMP, другие модули RK3506 и варианты DDR этим портом
не подтверждены. PicoCalc предоставляет дисплей, клавиатуру через STM32 и
отдельный слот microSD. Не путайте его с загрузочной microSD самой Lyra.

| Устройство         | Подключение                      | Параметры                                         |
|--------------------|----------------------------------|---------------------------------------------------|
| Загрузочная `sd0`  | SDMMC Lyra, `0xFF480000`         | SPL, OP-TEE, U-Boot, FIT; ручное чтение из LexxOS |
| Съёмная `sd1`      | SPI1, `0xFF130000`               | FAT32, `/mnt/sd`, чтение DMA/PIO, запись PIO      |
| LCD ILI9488        | SPI0                             | 320×320, RGB565, 46,875 МГц                       |
| STM32 клавиатуры   | I2C2, SDA GPIO0_B3, SCL GPIO0_B2 | Адрес `0x1f`, 100 кГц                             |
| Основная консоль   | UART0                            | 1 500 000 бод, 8N1                                |
| Отладочная консоль | UART1                            | 1 500 000 бод, включение командой `debug`         |

Распиновка съёмного слота PicoCalc:

| Сигнал                  | Вывод RK3506       | Контакт разъёма Lyra |
|-------------------------|--------------------|---------------------:|
| MOSI                    | RM_IO28 / GPIO1_C3 |                   19 |
| CLK                     | RM_IO29 / GPIO1_D1 |                   25 |
| CS, активный 0          | RM_IO30 / GPIO1_D2 |                   26 |
| MISO                    | RM_IO31 / GPIO1_D3 |                   27 |
| Card Detect, активный 0 | GPIO1_B2           |                   10 |

Все сигналы — 3,3 В; необходима общая земля. Нумерация относится к разъёму
Lyra/PicoCalc, а не к миниатюрному разъёму отладчика. UART1 использует те же
GPIO0_B2/B3, что I2C2 клавиатуры: это альтернативное назначение контактов,
одновременную работу на них предполагать нельзя.

## Сборка и загрузка

Нужны ARM GNU Toolchain (`arm-none-eabi-g++`, `objcopy`, GDB), CMake 3.25+,
Ninja и Python 3. Команды выполняются из корня репозитория.
Для 0.1.1 используется профиль `picocalc-lyra-release` с FreeRTOS, JCS,
управляемой MMU, DMA и периферией PicoCalc. Настройки прошивки перенесены из
аппаратно проверенной сборки FreeRTOS.

```sh
cmake --preset picocalc-lyra-release
cmake --build --preset picocalc-lyra-release
```

Профиль `picocalc-lyra` использует кооперативный планировщик.
Проверяйте сохранённые значения `CMakeCache.txt`: настройки прежней сборки
могут отличаться от новых значений по умолчанию. `DDR_EXTENDED` включён в
релизном профиле. `MANAGED_TIMER_IRQ=ON` несовместим с FreeRTOS.
`LEXXOS_RK3506_SHELL=OFF` оставляет ранний загрузочный режим, а не LexxCE.

Цепочка: BootROM → DDR/SPL → OP-TEE / U-Boot → FIT LexxOS и DTB →
ARM startup → FreeRTOS → Runtime / shell. Точка входа ELF — `0x02000000`.
Загрузчик должен передать управление с выключенными MMU/D-cache; прямой
U-Boot `go` не эквивалентен поддерживаемой передаче управления через `bootm`.

### Образы и установка

- `lexxos.elf`, `lexxos.bin`, `lexxos.map` — программа и отладочная информация.
- `lexxos.img` — дополнительно собираемый FIT для GPT-раздела `boot`, не файловая система и не
  образ всего диска. Упаковщик заменяет ядро, задаёт `load/entry=0x02000000`,
  проверяет SHA-256 и сохраняет DTB/resource. Подписанный FIT без возможности
  корректной переподписи изменять нельзя.
- `lexxos.uimg` — альтернативный legacy uImage для совместимого U-Boot.
- `sd-image-rk3506` создаёт полный `lexxos-sd.img`, манифест и SHA-256.
  Сборка не требует подключённой карты и сама ничего на неё не записывает.

Для полного образа используются закреплённые компоненты из
`third_party/rk3506-luckfox-lurra`; целый заводской `boot.img` не обязателен.
Подробности компонентов, размеров и разметки: [порт Lyra](../../ports/lyra/README.md).
Для полной установки есть `flash-rk3506`: размер берётся с выбранной карты,
создаётся полная резервная копия и проверяется чтение записанного образа.
При ручной подготовке образа задавайте `LEXXOS_LYRA_SD_SIZE_BYTES`, чтобы
резервная GPT оказалась в конце носителя. Холодный запуск новой карты требует
отдельной проверки; наличие собранного образа его не доказывает.

Для обновления существующей карты используйте свой шаблон FIT и собранное
ядро. На macOS:

```sh
python3 tools/rk3506_pack_fit.py --template boot-template.img \
  --input build/picocalc-lyra-release/lexxos.bin --output lexxos.img
python3 tools/flash_rk3506_macos.py --image lexxos.img --backup-dir work/backups/rk3506
```

Вторая команда интерактивна и изменяет карту после подтверждения. Скрипт
проверяет съёмный носитель и GPT, сохраняет резервную копию в
`work/backups/rk3506`, выполняет запись и сверяет чтение обратно. Не запускайте
`sudo cmake` и не записывайте FIT на весь диск. Номер `/dev/diskN` каждый раз
определяется заново; `LEXXOS_RK3506_FLASH_DISK` принимает целый диск только для
идентификации, а не как цель записи FIT. Исходная разметка Luckfox: `uboot`
с LBA `0x2000`, `boot` с `0x4000` длиной `0x6000` (12 МиБ), `rootfs` с `0x10000`.

Заставка U-Boot проверена пользователем 26.10.2026. Таргет `uboot-rk3506`
собирает её через Docker; `LEXXOS_RK3506_FLASH_BUILT_UBOOT=ON` включает
обновление U-Boot в `update-rk3506`. Альтернатива — готовый
`LEXXOS_RK3506_UBOOT_IMAGE`. При выключенной опции и пустом пути обновляется
только `boot`. См. [сборку U-Boot](../../ports/uboot/picocalc_lyra/README.md).

## Дисплей

Штатный режим: ILI9488 320×320, SPI0 46,875 МГц, RGB565 по два байта на пиксель,
DFS16 (`direct16`), два кадровых буфера общей ёмкостью 400 КиБ. В FreeRTOS
`lcd-present` получает запросы кадров отдельно от уведомлений завершения DMA.
`direct16` описывает формат SPI, а не прямое чтение кешируемой памяти DMA:
данные проходят через некешируемый промежуточный буфер.

Старый preset `picocalc-lyra-rgb565` оставлен для совместимости; отдельная
настройка RGB565 в новом `picocalc-lyra` не требуется. Если отключаете
`LEXXOS_ILI9488_RGB565_WIRE`, отключите и `LEXXOS_RK3506_LCD_DIRECT16_DEFAULT`.
При недоступном DMA предусмотрен PIO; частично выполненную DMA-передачу
нельзя просто повторять через PIO.

```text
display-test --bench --transport native --frames 500 --lcd-dma
display-test --bench --transport native --size gb1 --frames 500 --lcd-dma
display-test --bench --transport native --lcd-dma --lcd-packed8
```

`--lcd-packed8` временно выбирает проверочный путь и затем восстанавливает
режим. Измерения 28.10.2026: 500 полных кадров — 19,96 FPS; 500 кадров
160×144 — 33,17 FPS, без ошибок и тайм-аутов DMA. Это результаты конкретного
теста, а не гарантированная частота кадров приложений.

## Клавиатура PicoCalc

Lyra использует общий `PicoCalcKeyboard`, как платы Pico: раскладку, FIFO событий,
модификаторы, повторную инициализацию и передачу клавиш в shell обслуживает
существующая задача `picocalc-input`. Регистрируются `picocalc-keyboard`,
`picocalc-gamepad` и сервис southbridge. LCD для регистрации клавиатуры не требуется.

Основной backend — аппаратный I2C2 на GPIO0_B3 (SDA) и GPIO0_B2 (SCL).
`debug` и `system` обозначают одну физическую шину; адрес STM32 — `0x1f`.
Контроллер тактируется от OSC24M, скорость — 100 кГц. Передачи используют FIFO
по 32 байта, ACK промежуточных блоков чтения и NACK последнего байта. NACK и
тайм-аут возвращаются как ошибка; после каждой операции выполняются STOP,
отключение контроллера и очистка флагов. Лимит передачи — 20 мс плюс до 20 мс
на STOP при ошибке. События контроллера опрашиваются синхронно; доставка I2C2
через GIC замаскирована. IRQ-обработчик и DMA не используются.

Настройки clock/pinmux/reset сверены с
[RK3506 TRM v1.2 Part1](https://rockchip.fr/Rockchip%20RK3506%20TRM%20V1.2%20Part1.pdf)
(главы CRU, GPIO0 IOC, RM_IO и I2C) и
[драйвером clock в Linux](https://github.com/torvalds/linux/blob/master/drivers/clk/rockchip/clk-rk3506.c).
Изменяются только поля I2C2; clock/reset SPI0 и SPI1 сохраняются.

### Переключение на программный I²C

Для диагностики доступен общий
[`SoftwareI2cBus`](../../src/lexxos/devices/bus/software_i2c_bus.h).
Он не содержит адресов RK3506 и использует переданные callbacks настройки GPIO,
open-drain release/read и монотонного счётчика с известной частотой. Подключение
к другой платформе требует реализации этих callbacks; протокол переносится без изменений.
Callback `configure` должен оставить обе линии отпущенными, а `release(..., false)`
должен тянуть линию к нулю, никогда не выдавая высокий уровень push-pull.
Драйвер рассчитан на единственного master, скорости 1–100 кГц, поддерживает
clock stretching, тайм-ауты и до девяти импульсов восстановления занятой SDA.

Переключение существующей сборки Lyra:

```sh
cmake --preset picocalc-lyra-release -DLEXXOS_RK3506_I2C_BACKEND=software
cmake --build --preset picocalc-lyra-release
```

Возврат к основному варианту:

```sh
cmake --preset picocalc-lyra-release -DLEXXOS_RK3506_I2C_BACKEND=hardware
cmake --build --preset picocalc-lyra-release
```

Для новой сборки значение по умолчанию — `hardware`. Выбор сохраняется в CMake cache;
автоматического перехода на другой backend при ошибке нет. В UART при инициализации
выводится `picocalc i2c: hardware I2C2...` либо `picocalc i2c: software GPIO0_B3/B2...`.
Переключение требует пересборки и загрузки нового образа, команды выше не прошивают плату.

Между выбором регистра STM32 и чтением ответа сохраняется задержка 2 мс. Она и
передача выполняются без переключения задач: это сохраняет целостность транзакции
в ранней cooperative-сборке CPU0. Для актуальной FreeRTOS-сборки
смотрите [статус интеграции](#аппаратные-результаты); полноценный аудит
конкурентного доступа и SMP остаётся отдельной задачей. Аппаратный backend формирует сигналы самостоятельно,
но polling и задержка ответа всё ещё занимают CPU.

По умолчанию выбирается заводская прошивка STM32. Если на STM32 уже установлена JCS,
передайте при конфигурации `-DLEXXOS_PICOCALC_KEYBOARD_FIRMWARE=jcs`, как для Pico.
Эта опция выбирает протокол LexxOS, но не прошивает STM32. Скорость Lyra пока
фиксирована в board descriptor; `LEXXOS_PICOCALC_SYSTEM_I2C_BAUDRATE` относится к Pico.

Проверка на плате (для `keyboard-live` включите тестовые команды клавиатуры):

```text
i2c-scan --bus system --from 0x1f --to 0x1f
picocalc-info
keyboard-live -s 30 -f picocalc-keyboard
```

Ожидается ответ на `0x1f`, успешное чтение состояния и события нажатия/отпускания.
Проверьте ввод букв и цифр в shell, Shift/Ctrl/Alt, стрелки, Enter, Backspace,
удержание клавиш и повторный запуск через SWD. При отсутствии ответа STM32 UART-shell
должен оставаться доступен; зарегистрированный драйвер повторяет инициализацию.

Программно проверены аппаратная сборка factory с LCD и программная JCS без LCD,
контрактные тесты раскладки и southbridge, задержка ответа RK3506 и тесты обоих
backend на границы FIFO, порядок байтов, ACK/NACK, тайм-ауты и повторный обмен
после ошибок. Реакция клавиатуры на реальной Lyra отдельно подтверждена автором
при подготовке 0.1.1.

## Носители и файловая система

| Носитель | Шина / назначение                             | Политика                                                                               |
|----------|-----------------------------------------------|----------------------------------------------------------------------------------------|
| `sd0`    | SDMMC Lyra: SPL, OP-TEE, U-Boot, FIT          | Системная, manual, `default-ro`, не затрагивается PicoCalc storage service             |
| `sd1`    | SPI1 PicoCalc: съёмные FAT32 файлы приложений | `default-rw`; автоматически монтируется в `/mnt/sd` при запуске FreeRTOS с peripherals |

Плата уже объявляет `picoCalcLyraStoragePolicy` с `sd1.readOnlyByDefault=false`. В FreeRTOS больше **нет**
дополнительного слоя, принудительно ставящего `readOnlyByDefault=true`. После успешного card-detect, probe и проверки
55AA сектора 0 сервис применяет политику RW перед mount FatFs.

Для нормальной сборки дополнительные флаги `LEXXOS_RK3506_SD_WRITE_EXPERIMENTAL` и `LEXXOS_RK3506_SD_MOUNT_RW_AT_BOOT`
**не требуются** и игнорируются как устаревшие. Если необходима аварийная RO-прошивка, установите
`LEXXOS_RK3506_SD_FORCE_READ_ONLY=ON` — он переводит **только sd1** в политику read-only и запрещает команду ручного
разрешения RW.

### Переходы состояний

- **Загрузка:** `sd1` проверяется и при нормальных условиях монтируется в FAT RW; при отсутствии/ошибке карты ОС
  продолжает работу без тома.
- **Обычное размонтирование:** `sd-media unmount` выполняет штатное закрытие FatFs и очищает `writeArmed`. Следующий
  `sd-media mount` снова использует board default, то есть RW.
- **Явный RO:** сначала `sd-media unmount`, затем `sd-media rw off`, затем `sd-media mount`. Этот выбор сохраняется при
  ручном remount текущей сессии.
- **Возврат RW:** размонтировать, выполнить `sd-media rw on I-ACCEPT-DATA-LOSS` и снова смонтировать. На обычном старте
  `rw on` не требуется.
- **Ошибка секторной записи:** `writeArmed` отключается; ошибка запоминается, повторная попытка автоматически разрешить
  RW отклоняется. Для повторной записи требуется новая сессия после наблюдаемого извлечения/перезапуска и диагностика
  FAT.
- **Hotplug:** после начального монтирования FreeRTOS запускает задачу `sd-hotplug` (период опроса 100 мс). При
  извлечении доступ к карте немедленно блокируется и недействительный FAT-том принудительно снимается; после устойчивого
  отсутствия (3 опроса) и повторной вставки карта автоматически определяется и монтируется в штатном RW, если
  `sd-media auto off` не задана вручную.
- **Предупреждение:** автоматический `forceUnmount` при физическом извлечении не может сохранить незавершённые
  FAT-записи. Перед плановым извлечением выполняйте `sync` и `sd-media unmount`; hotplug предназначен для восстановления
  доступности, не для гарантии атомарности записи.

### Проверка в shell

На рабочей тестовой карте после загрузки:

```text
sd-media status
write /mnt/sd/rw-boot.txt BOOT_RW
append /mnt/sd/rw-boot.txt SECOND
cat /mnt/sd/rw-boot.txt
sync
sd-media unmount
sd-media mount
sd-media status
cat /mnt/sd/rw-boot.txt
```

Оба `sd-media status` должны показывать `/mnt/sd rw` и `default-rw` для `sd1`. Для проверки RO отдельно:

```text
sd-media unmount
sd-media rw off
sd-media mount
sd-media status
```

Ожидается `/mnt/sd ro` при неизменной политике платы `default-rw`. Карта `sd0` остаётся
`system fixed manual default-ro`.

Низкоуровневая запись остаётся CMD24 через SPI1 PIO с CRC16, проверкой Data Response, busy, CMD13 и немедленным
readback. SD PL330 RX DMA применяется только при чтении; показания `mem dma-stats` не отражают скорость записи. Перед
физическим извлечением всегда выполняйте `sync` и успешный `unmount`. Обрыв питания во время записи всё ещё способен
повредить FAT.

### Регрессионный статус

04.11.2026 на предыдущей конфигурации подтверждены `write`, `append`, `cp`, `sync` и повторное чтение после RO remount,
без аппаратных ошибок SD/LCD DMA. Новая правка меняет **только выбор режима монтирования**, а не протокол CMD24, FatFs
или DMA. Перепроверьте короткий сценарий из раздела выше после прошивки; полный soak и проверка аварий назначаются на
выпуск нового релиза.

### Проверка восстановления после извлечения (новый путь)

1. После загрузки убедитесь, что `sd-media status` показывает `/mnt/sd rw` и `automount: on`.
2. Убедитесь, что `cat /mnt/sd/rw-boot.txt` работает. Завершите `sync` и `sd-media unmount`, физически извлеките SD и
   через 0,5–1 с проверьте `sd-media status`: том должен быть снят и карта отсутствовать.
3. Вставьте SD обратно, подождите 0,5–2 с (на ошибках probe автоматическая повторная попытка через 2 с), затем проверьте
   `sd-media status` и `cat /mnt/sd/rw-boot.txt`.
4. После явного `sd-media unmount` без физического извлечения автоматического подключения **не должно** быть. После
   подтверждённого извлечения и новой вставки автомонтирование возобновляется.
5. При ошибке записи не выполняется автоматическое повторное разрешение RW до подтверждённого извлечения носителя. `sd0`
   не затрагивается.

Автоматическая обработка извлечения и повторной установки проверена автором
на реальной Lyra при подготовке 0.1.1.

## Память и MMU

Управляемая MMU использует L1 и страницы L2 по 4 КиБ, VA=PA, только CPU0.
Граница RX/RW выровнена на 4096 байт; код доступен только для чтения и
исполнения, данные — RW/XN. Это ещё не изоляция процессов, пользовательский
режим или полноценный менеджер всех 128 МиБ DDR.

| Область                                    | Назначение и атрибуты                                        |
|--------------------------------------------|--------------------------------------------------------------|
| `0x00000000..0x01FFFFFF`                   | Резервы загрузчика/FDT, Normal-NC, RW/XN; не выдаются LexxOS |
| `0x02000000..__rx_end__`                   | Код и константы ядра, WBWA, RO, исполняемые                  |
| `__rx_end__..__image_end__`                | Данные, стеки, таблицы страниц и куча FreeRTOS, WBWA, RW/XN  |
| `align_up(__image_end__,4096)..0x02600000` | Пул страниц LexxOS; свободные страницы не отображены         |
| `0x02600000..0x026FFFFF`                   | Зарезервированная рабочая область загрузчика, не отображена  |
| `0x02700000..0x027EFFFF`                   | Резерв DMA Normal-NC; внутри него отдельный пул 256 КиБ      |
| `0x027F0000..0x027FFFFF`                   | Резерв монитора GDB, не отображён                            |
| `0x02800000..0x07FFFFFF`                   | Остальная DDR, не считается свободной памятью LexxOS         |
| `0x08000000..0xFFFFFFFF`                   | Периферия, Device, RW/XN                                     |

Диапазон резерва DMA больше самого 256-КиБ пула: их размеры нельзя смешивать.
OP-TEE, U-Boot, FDT, VOP и другие компоненты могут сохранять владение DDR
после передачи управления. Расширение требует проверки резервов прошивки.

### Страницы и DMA-буферы

`allocateOwnedPages()` выдаёт обнулённые страницы WBWA, не более 64 страниц (256 КиБ) за один запрос. При освобождении
выполняются очистка/инвалидация
D-cache, удаление отображения, очистка PTE и инвалидация TLB CPU0. Обращение
к освобождённой странице вызывает исключение. Пул не предназначен для DMA
или ISR и не заменяет автоматически кучу и стеки FreeRTOS.

`memory::allocateDma/freeDma/isDmaBuffer` работают с отдельными физическими
4-КиБ страницами Normal-NC. Обнуление не гарантировано. `cleanForDevice`,
`invalidateFromDevice` и `cleanInvalidate` допустимы только для памяти,
которой владеет вызывающая сторона; неполные строки кеша при инвалидации
отклоняются. Время жизни буфера, последовательность операций и отсутствие
одновременной записи CPU во время DMA обеспечивает драйвер.

```text
mem map
mem pages
mem page-test
mem dma-test
mem regions
mem fdt
mem
```

`mem page-test` проверяет две страницы (8 КиБ) и восстановление счётчиков;
ожидается `page test: ok`. Намеренно читать освобождённую память нельзя.
При Data Abort сохраните PC/DFSR/DFAR и восстановите рабочий образ.

### Дополнительные 8 МиБ DDR

`LEXXOS_RK3506_DDR_EXTENDED=ON` отдельно включает диапазон
`0x02800000..0x02FFFFFF`: 2048 страниц WBWA/RW-XN по 4 КиБ. Нужны FreeRTOS,
управляемая MMU и выключенный SWD RAM reload. Режим выключен по умолчанию:
расположение U-Boot в одном журнале не доказывает доступность этих адресов
на любой версии платы или прошивки.

Страницы отображаются и обнуляются по запросу, снимаются с отображения при
освобождении; предел одного выделения — 1 МиБ. `ProgramMemoryArena`
направляет сюда рабочие области от 4 КиБ, меньшие остаются в `heap_4`.
Стеки задач и куча ядра не перемещаются. Пул **не подходит для PL330 DMA**.
`mem extended-test` должен вернуть `extended DDR test: ok`, до и после
свободно 2048 страниц и нет активных выделений. Тест FAT RW от 04.11.2026
не подтверждает право владения этой областью.

### Память приложений и стеки

`LEXXOS_RK3506_FREERTOS_HEAP_KIB` задаёт бюджет `heap_4`: по умолчанию
512 КиБ, допустимо 128–2048. Это не объём всей DDR. Кооперативные 256 КиБ
кучи и 96 КиБ пула стеков относятся к другому планировщику и не суммируются
с этим бюджетом. См. [общие профили памяти](../runtime-memory-profiles.md).

В 64-байтном заголовке LEXX v1 `memorySize` (смещение 32) — всё гостевое
адресное пространство, включая образ, BSS, стек, аргументы и гостевую кучу.
`stackSize` находится по смещению 36, `bssSize` — 40. Предел гостя — 65536 байт,
даже при увеличенной куче FreeRTOS. `lexx-run` сначала проверяет заголовок
и индекс ресурсов, затем резервирует `memorySize` через `ProgramMemoryArena`.
При отказе выдаётся `memory-unavailable requested=N free-heap=M`; частичный
образ не запускается. `free-heap` не гарантирует непрерывный блок такого размера.

```sh
python3 tools/lexx_pack.py app.bin app.lexx --elf app.elf --memory 16384 --stack 4096
```

Упаковщик проверяет образ, стек и `.bss` ELF, но статический анализ не
предсказывает пик динамической кучи. Старые файлы v1 могут включать весь
свободный остаток в `bssSize`; равенство суммы полей не требуется.
После выхода приложения арена должна освобождаться. Проверяйте `mem`,
`tasks` и `jobs`, в том числе на ошибках запуска и слишком большом запросе.

## DMA и прерывания

PL330 DMAC0: каналы/события 0 и 1 принадлежат SD SPI1, канал/событие 2 — LCD
SPI0. Запрос 2 обслуживает SPI1 TX (такты `0xff` при чтении), запрос 3 — RX.
Микропрограммы PL330 и передаваемые данные размещаются в выделенном
Normal-NC пуле; интерфейс запуска отвергает код за его пределами.

SD использует 512-байтный промежуточный буфер NC. Прямой RX допустим только
в зарегистрированный NC-буфер. LCD копирует RGB565/RGB666 в блоки по
4/8/16/32 КиБ (обычно 16 КиБ), ждёт завершения DMA и опустошения FIFO SPI0.
Исходный буфер сохраняется до завершения. Драйверы удерживают NC-память до
перезагрузки; если двигатель нельзя остановить, память изолируется, а не
возвращается другому владельцу. Повторение частичной передачи через PIO запрещено.

Расход пула: SD 4 КиБ, LCD размер блока + 4 КиБ кода. При блоке 16 КиБ
занято 24 КиБ, свободно 237568 байт из 262144. `mem dma-stats` снимает
счётчики в короткой критической секции; форматирование и UART идут после неё.

### Завершение LCD и настройка пакетов

`LCD_DMA_NOTIFY_ISR=ON` использует отдельный двоичный семафор. Уведомление
задачи о новом кадре для этого не используется. ISR подтверждает только событие
LCD 2 и вызывает `xSemaphoreGiveFromISR()`. Числовой приоритет GIC должен
читаться как минимум `0x90` (настраивается `0xA0`). Ожидание по 1 мс позволяет
перепроверять ошибки PL330 и общий тайм-аут; такие пробуждения не равны
аппаратным тайм-аутам передачи.

`LCD_DMA_BURST_UNITS` принимает 1, 2 или 4; по аппаратному сравнению выбран 2.
Настройка касается RGB565 DFS16. Если длина не кратна `burstUnits * 2`, весь
блок передаётся с burst=1. Режимы SD и порог FIFO SPI0 не меняются.
`LCD_DMA_DRAIN_SPIN_US` ограничивает активное ожидание хвоста FIFO:
0/50/100/200/500 мкс, обычно 200. После предела задача засыпает.

`LCD_DMA_WAIT_WFE=ON` — отдельный эксперимент, несовместимый с
`LCD_DMA_NOTIFY_ISR=ON`. В рабочем измерении от 04.11 он выключен. При
сравнении сохраняйте одинаковые частоту SPI, размер блока и нагрузку,
проверяйте изображение, ввод с клавиатуры, SD CRC и остаток пула.

### GIC и диагностика

GICv2: Distributor `0xFF581000`, CPU Interface `0xFF582000`. В DTB DMAC0
`@ff000000` имеет SPI 116/117, то есть абсолютные INTID 148/149; DMAC1
`@ff008000` — INTID 150/151. Назначение второго выхода 149 не подтверждено,
он не включается. Прежнее использование GIC55 было ошибкой.
Generic Virtual Timer PPI27 даёт тик FreeRTOS; CNTVCT/CNTFRQ — 24 МГц,
это частота счётчика времени, а не Cortex-A7.

В диагностической сборке (`LEXXOS_RK3506_SD_DIAGNOSTICS=ON`):

```text
irq-list
irq-list all
irq-list 148
irq-list pending
irq-list handled
sd-diag dma irq-info
mem dma-stats
```

`irq-list` показывает INTID, SGI/PPI/SPI, EN/PD/AC, тип L/E, приоритет,
целевой CPU и HITS. HITS учитывает чтения IAR именно CPU0 LexxOS, не Secure
world или другие CPU. Диагностическая команда сама не читает IAR и не
перенастраивает GIC/GRF. В Non-secure режиме `group=unknown` и нулевые
значения защищённых регистров могут означать RAZ/WI; они не опровергают
реально полученные ISR-события. Не сбрасывайте общий GIC/DMAC0 из драйвера.

### Проверка совместной работы

После холодного старта запишите `mem map`, `mem fdt`, `mem regions`,
выполните `mem dma-test`. Проверьте сообщения включения LCD/SD DMA,
чтение `ls`/`cat`, запуск и выход из `.lexx`, одновременно обновляя экран.
Сравните `mem dma-stats` до и после: ошибки/аппаратные тайм-ауты нулевые,
счётчики IRQ растут, резерв NC стабилен. При отказе используйте проверенный
образ с `DMA_SAFE=OFF`; проверка микропрограммы на компьютере не заменяет
проверку изображения и данных на плате.

## Отладка UART и SWD

Загрузка всегда начинается с существующей системной SD и UART0. SWD и UART1
не включаются автоматически. Управляемая MMU/D-cache несовместима с текущим
монитором перезаписи DDR: он требует `SCTLR.M=0`, `SCTLR.C=0`. Ограничение
относится к протоколу загрузки, а не к способности Cortex-A7 отлаживаться с MMU.
Используйте отдельную сборку `picocalc-lyra-debug` с отключёнными MMU/DMA_SAFE
и включённым `LEXXOS_RK3506_SWD_DEBUG`.

| Контакт Lyra | RK3506             | Функция     | Raspberry Pi Debug Probe |
|--------------|--------------------|-------------|--------------------------|
| 8            | GPIO0_B2 / RM_IO10 | UART1 TX    | UART RX                  |
| 9            | GPIO0_B3 / RM_IO11 | UART1 RX    | UART TX                  |
| 1            | GPIO0_C6 / RM_IO22 | SWCLK       | SWCLK                    |
| 2            | GPIO0_C7 / RM_IO23 | SWDIO       | SWDIO                    |
| GND          | GND                | Общая земля | Земля обоих разъёмов     |

Не подключайте контакты 1/2 одновременно к UART0 и SWD. Подключайте проводку
при выключенном питании; переключатель должен размыкать старую цепь до
замыкания новой. Не подавайте 5 В и не питайте Lyra от отладчика. SRST не нужен.

```text
debug status
debug uart mirror
debug uart 1
debug uart 0
debug swd on
```

`mirror` выводит в обе консоли, ввод UART1 имеет приоритет. Сначала проверьте
UART1 TX/RX. `debug swd on` оставляет только UART1 и переключает GPIO0_C6/C7
на SWD Cortex-A7; возврат UART0 требует холодного старта. Старые CMake
`LEXXOS_RK3506_CONSOLE` и `LEXXOS_RK3506_ENABLE_SWD` больше не выбирают маршрут.
Журнал U-Boot остаётся на исходном UART0.

```sh
openocd -f tools/debug/openocd/lexxos-rk3506-cmsis-dap.cfg
```

Ожидаются DPIDR `0x2ba01477`, цель `rk3506.a7` и GDB-порт 3333. При проблемах
проводки снижайте `adapter speed` до 200. Не выполняйте `reset halt`,
`reset init`, `program` или `flash write_image`: DDR настраивается загрузчиком,
а перезапуск SoC может отключить SWD. Подключение без загрузки требует ELF,
точно соответствующего коду в DDR (`Download=Never`, `Reset=None`).

Ручная перезагрузка: остановите файловые операции, выполните `debug ram prepare`
по UART1, подключитесь с новым ELF через `tools/debug/gdb/rk3506-ram.gdb`,
затем явно вызовите `lexxos_ram_reload`, при необходимости
`compare-sections .text` и `continue`. Подготовка проверяет DMA/cache,
маскирует IRQ/FIQ/PPI27 и останавливает ОС. Это не перезапуск SoC; при
ошибке загрузки восстановление — холодный старт с SD. Кнопка RECOVERY/BOOT
относится к SARADC/режиму загрузки ROM; включение SWD удержанием три секунды
не реализовано.

## CLion и обновление DDR

### Готовые конфигурации проекта

Файлы `.run` добавляют следующие пункты в список Run/Debug:

| Конфигурация               | Действие                                                                    |
|----------------------------|-----------------------------------------------------------------------------|
| `LexxOS Lyra Reload Check` | Проверяет тесты, ARM GDB и dry-run без платы; использовать **Run**          |
| `LexxOS Lyra OpenOCD`      | Запускает постоянный сервер OpenOCD; использовать **Run**                   |
| `LexxOS Lyra RAM Debug`    | Собирает Debug ELF, обновляет DDR, подключает CLion; использовать **Debug** |
| `LexxOS Lyra RAM Attach`   | Только подключает CLion к уже загруженному ELF; использовать **Debug**      |
| `LexxOS Lyra RAM Upload`   | Служебный шаг Before launch для RAM Debug                                   |

Старый `LexxOS Lyra Attach` типа OpenOCD Download & Run оставлен для прежнего сценария.
Не запускайте его одновременно с новым постоянным сервером: оба используют порт 3333.

В RAM Debug уже указан Before launch → Run Another Configuration →
`LexxOS Lyra RAM Upload`. Отдельный глобальный External Tool создавать не нужно.
Служебный шаг выполняет configure/build и загрузку последовательно; ошибка прерывает запуск.

Общий профиль `picocalc-lyra-debug` собирает `build/picocalc-lyra-debug/lexxos.elf`
с `CMAKE_BUILD_TYPE=Debug`. Этот же файл указан как Symbol file в обеих Remote Debug
конфигурациях.

Для Shell-конфигураций сделайте `python3`, `openocd` и `arm-none-eabi-gdb`
доступными в `PATH` CLion.

### Первый запуск с платой

1. Загрузите плату с рабочей SD-прошивкой, поддерживающей `debug swd on`.
2. Подключите UART1 для дальнейшей консоли, скорость **1500000** бод.
   Через доступную консоль выполните `debug swd on`. После холодного включения это
   нужно повторять: программа не может включить SWD, если доступа к CPU ещё нет.
3. Подключите Raspberry Pi Debug Probe: SWCLK/SWDIO и общую землю, соблюдая
   [схему подключения и переключения UART0/SWD](#отладка-uart-и-swd).
   После переключения UART0 больше не используется как консоль.
4. Выберите `LexxOS Lyra OpenOCD` → **Run**. Дождитесь сообщения о GDB-порте 3333.
5. В новых версиях CLion выберите в верхней панели **Debug Profile → arm-none-eabi-gdb**.
   Выберите toolchain с `arm-none-eabi-gdb` в Run → Edit Configurations
   для обеих RAM-конфигураций.
   Поставьте breakpoint, например на первой инструкции `rk3506_early_main` или в `Runtime::run`.
   Выберите `LexxOS Lyra RAM Debug` → **Debug**.
6. Загрузчик оставляет CPU на `_start`, до исполнения новой прошивки. CLion
   подключается с соответствующими символами и может автоматически продолжить
   исполнение до установленного breakpoint (так происходит с текущим Debug Profile).
   Поэтому ставьте breakpoint до запуска. После остановки нажмите **Resume**.

Перед повторным Debug остановите предыдущую сессию CLion. OpenOCD оставьте запущенным.
Не должно быть двух GDB-клиентов одновременно. Для RAM Attach ELF на диске должен
точно соответствовать образу в DDR; эта конфигурация не собирает и не загружает код.

### Повторная сборка и отладка

1. Остановите текущую сессию **Debug** в CLion; сервер OpenOCD оставьте запущенным.
2. Измените код и выберите `LexxOS Lyra RAM Debug` → **Debug**.
3. Before launch сам выполнит configure/build, проверку состояния CPU и загрузку DDR.
4. Дождитесь подключения CLion и нажмите **Resume**. Не запускайте RAM Upload параллельно.

После выключения питания изменения DDR теряются: плата снова загружается с SD.
Повторите `debug swd on` и при необходимости перезапустите OpenOCD. Чтобы новый код
сохранялся после выключения, потребуется отдельно собрать FIT и обновить SD по
[инструкции платы](picocalc_lyra_m.md). Обычный RAM Debug этого не делает.

Если нужно только исследовать уже работающую прошивку, выберите
`LexxOS Lyra RAM Attach` → **Debug**, не пересобирая соответствующий ELF.
При отсутствии платы доступен `LexxOS Lyra Reload Check` → **Run**.

### Что делает загрузчик

`tools/rk3506_debug_reload.py` подключается к существующему OpenOCD. До записи DDR
проверяет отключение MMU/D-cache через CP15 и принадлежность GPIO0_C6/C7 интерфейсу SWD.
Инвалидирует I-cache и branch predictor перед исполнением нового монитора.

Отдельный assembly-монитор занимает зарезервированную область `0x027f0000` вне ELF.
Он не использует stack, heap, shell или функции старой прошивки. Проверяет состояние
DMAC0 manager, восьми каналов и регистров ошибок; отключает локальный таймер и известные
DMA IRQ, отключает I-cache. Только статус `RAMO` разрешает команду GDB `load`.
Linker assertion и проверка `__image_end__` запрещают пересечение нового ELF с монитором.

`--stay-halted` оставляет CPU на `_start` для CLion. Без этого параметра загрузчик
запускает новую прошивку сразу. SD при загрузке не перезаписывается; `reset init`,
`program` и `flash write_image` не используются.

```bash
python3 tools/rk3506_debug_reload.py \
  --configure-preset picocalc-lyra-debug \
  --build-dir build/picocalc-lyra-debug \
  --elf build/picocalc-lyra-debug/lexxos.elf --mode swd --stay-halted
```

`--mode uart --port /dev/cu.usbmodemXXXX` сначала требует подтверждения
`debug ram prepare` через UART1. `--mode auto` пробует UART, а при отсутствии ответа
переходит к SWD. В обоих случаях монитор всё равно проверяет состояние CPU/DMA.
Для UART нужен `pyserial`, а последовательный порт не должен быть занят терминалом.
Режим `swd`, выбранный в CLion, не требует UART для каждого обновления.

### Проверки без платы и границы восстановления

```bash
python3 tools/test_rk3506_debug_reload.py
python3 tools/rk3506_debug_reload.py --dry-run --stay-halted
cmake --preset picocalc-lyra-debug
cmake --build --preset picocalc-lyra-debug
```

`--dry-run` только печатает GDB-сценарий: не собирает и не подключается к плате.
Host-тесты также включены в CTest как `lexxos_rk3506_debug_reload_tests`.

Отказ `CACH` означает включённые MMU/D-cache, `DMAB` — занятый DMAC0,
`DMAF` — ошибку manager или канала. Зависший shell можно обойти только при уже
включённом SWD и выполнении этих условий. Это восстановление CPU0, а не полный
reset SoC: другие ядра, неизвестные DMA masters и занятая старой прошивкой scratch-область
не покрываются проверкой. Не обновляйте DDR во время записи файлов на SD.
После неудачи загрузки DDR может содержать частично новый образ; восстановление —
холодная загрузка с SD. Автоматический reset не выполняется.

На плате 25.10.2026 проверены SWD через Raspberry Pi Debug Probe на 1000 кГц,
проверка монитора (`RAMO`), загрузка Debug ELF в DDR (1 006 464 байта) и подключение
CLion с остановкой в `rk3506_early_main`. Полный цикл RAM Debug с Before launch также прошёл с остановкой на строке 311.
После Resume прошли `.data`, `.bss`, `.init_array`, IRQ self-test и запуск shell.
В UART-консоли команда `debug status` подтвердила UART1 и `SWD: on`.
Аппаратный reset не потребовался.
Host-проверки включают регрессию ошибки GDB `restore`: имя `monitor.bin` передаётся
без кавычек относительно временного каталога, установленного через `--cd`.

Если CLion сообщает `Undefined info command: "pretty-printer"`, установленный GDB
собран без Python: обычные breakpoint/step работают, Python pretty-printers недоступны.
Это отдельное предупреждение, не ошибка подключения к SWD.

Скорость UART-консоли — 1 500 000 бод.
SWD использует USB CMSIS-DAP, CLion подключается к `127.0.0.1:3333`.
Перед запуском Debug сервер OpenOCD должен уже работать; второй экземпляр не запускайте.

Основа конфигурации: [Remote Debug в CLion](https://www.jetbrains.com/help/clion/remote-debug.html).
Команды CP15: [OpenOCD ARM commands](https://openocd.org/doc/html/Architecture-and-Core-Commands.html).

> При `LEXXOS_RK3506_MMU_MANAGED=ON` существующий SWD RAM-reload монитор не применяется: он требует отключённых
> MMU/D-cache. Используйте отдельный SWD-safe preset; аппаратная возможность SWD сама по себе не исчезает.

## Архитектура порта

`app::Runtime` подключает общие `OperatingSystem`, `ProgramManager`, shell,
VFS и FatFs; транспорт передаёт стандартный `BlockDevice`. Композиция в
`src/lexxos/composition/board_runtime.cpp` задаёт сервисы платы и запускает
LCD и `sd-hotplug` после начального монтирования.

| Область исходников                     | Ответственность                                                         |
|----------------------------------------|-------------------------------------------------------------------------|
| `platform/rockchip/rk3506/`            | Запуск ARM, исключения, GIC/таймер, UART, MMU и платформенные механизмы |
| `devices/rk3506/picosd_transport.*`    | SD SPI, команды/CRC, проверка записи                                    |
| `devices/rk3506/picosd_spi1_hw.*`      | Контроллер SPI1 и FIFO                                                  |
| `devices/rk3506/picosd_dma_pl330.*`    | Реализация PL330 для SD                                                 |
| `devices/rk3506/picosd_block_device.*` | Границы LBA, режим RO, запрет повторной записи после ошибки             |
| `app/rk3506/picosd_storage.*`          | Политика слота, устранение дребезга, автомонтирование и восстановление  |
| `app/rk3506/picosd_mount_policy.*`     | Адаптер `StorageMountPolicy`                                            |
| `apps/storage/rk3506/`                 | Специализированная диагностика и тесты скорости                         |

Транспорт не включает ProgramManager, AppContext или VFS. `PicoSdMediaHooks`
передают проверку занятости и запрет повторного автоматического определения
карты; до подключения этих функций операции, требующие проверки владения,
запрещены. Снимки диагностики доступны через `picosd_diagnostics.h`.
Историческое пространство имён не определяет физическое размещение модуля.

`StorageMountPolicy` принадлежит экземпляру ОС: `prepareMount()` вызывается
до FatFs, `mountFinished()` получает результат, `unmounted()` — уведомление
только после успешного размонтирования. Срок жизни обеспечивает композиция.
Общие `mount`/`umount` не должны знать RK3506 и имя `sd1`. При неудачном
монтировании разрешение записи снимается; явное размонтирование подавляет
автомонтирование до извлечения. Сервис получает явные `SdMediaTransport`
и `FatMountBackend`; изоляция проверяется контрактными тестами.

Проверки на компьютере: `lexxos_rk3506_storage_tests` (LBA, RO, ошибки,
неприкосновенность `sd0`) и `lexxos_services_contract_tests` (политики и
изоляция экземпляров ОС). Они не проверяют MMIO и электрические сигналы.
При изменении порта нужны сборки с диагностикой OFF/ON и без shell, затем
аппаратная проверка загрузки, терминала, FAT, ручного монтирования и hotplug.
Не включайте общий `SD_CARD` ради объединения кода без проверки выбора слота.

### Статус приёмки

**Подтверждено аппаратно на предыдущей сборке:** boot RW с opt-in флагами, создание/добавление/чтение текста,
копирование `.lexx`, успешный `FileHandle::finish()`, `sync`, сброс RW после unmount и последующий RO mount, отсутствие
ошибок DMA. **После изменения штатной политики:** новый код должен давать RW после boot *и* обычного ручного remount;
этот переход ещё не проверен на устройстве.

**Пока не подтверждено этим журналом:** проверка совпадения хешей/метаданных на компьютере, холодный перезапуск с
проверкой обоих файлов, заполнение носителя, имитация сбоев FatFs на физической карте, извлечение/потеря питания во
время записи, продолжительный стресс с конкурентными I/O. Последние два сценария допускаются только на расходной карте и
**не** являются условием безопасной обычной работы FAT при штатном выключении.

Практический критерий: функциональный этап `SD RW / FAT` для `sd1` завершён; не присваивать статус «устойчиво к
аварийному питанию» или «production proven» без отдельных испытаний. Следующий программный риск — недостаток стека у
простых файловых команд.

Ранняя SDMMC-диагностика ограничивала GPT записями по 128 байт, массивом
до 64 КиБ и резервным LBA не выше `0x007fffff`; ёмкость выводилась из
проверенной GPT, а не CSD. Эти ограничения не следует переносить на
пользовательскую `sd1`, ёмкость которой определяется по CSD. Штатный rootfs
может быть ext4; отказ FAT32 не является поводом форматировать системную карту.

CRC16 SD использует полином `0x1021`, начальное значение 0. Режим `table`
занимает 512 байт таблицы, `slice4` — около 2 КиБ. В старом тесте CMD18,
1024 сектора, 12 МГц/FIFO fast: из 2432 мс около 1525 занимал побитовый CRC,
412 — FIFO, 401 — тестовый FNV1a. Ускорение CRC оценивалось отдельно от DMA.
`read` без времени FNV1a — оценка секторного чтения, `verified` включает
хеширование; ни одно не является скоростью FAT.

### Прежние режимы MMU и измерение VM

`MMU_NORMAL_NC` отображал 128 МиБ секциями по 1 МиБ без D-cache.
`DCACHE_BOOTRAM` добавлял WBWA только для `0x02000000..0x027FFFFF`, требовал
FreeRTOS и отключал PL330. Это отдельные режимы, не текущий `MMU_MANAGED`.
Старый запрет DMA при кешировании снят только для нового пути с NC-буферами,
а не для произвольной DDR. SWD RAM reload по-прежнему требует выключенных кеша/MMU.

```text
bench --profile vm-detail --vm-case control.loop --vm-repeat 5 --iterations 10000 --no-save --no-display --no-mirror
bench --profile vm-detail --vm-case load. --vm-repeat 5 --iterations 10000 --no-save --no-display --no-mirror
bench --profile vm-detail --vm-case mix. --vm-repeat 5 --iterations 10000 --no-save --no-display --no-mirror
bench --profile vm-detail --vm-case op.sra --vm-repeat 5 --iterations 10000 --no-save --no-display --no-mirror
```

`control.loop` — две инструкции RV32I за итерацию; его стоимость нельзя
автоматически вычитать из остальных тестов. Сохраняйте одинаковые частоту
CPU, профиль VM, число итераций и вывод, сравнивайте минимум два холодных
старта. CNTVCT измеряет время; `ns-per-inst` не определяет частоту CPU.

### WFE и PMU

База 03.11.2026 с блоком LCD 16 КиБ: SD 61 сектор, 828 КиБ/с;
LCD 162 блока, 3433 КиБ/с, без ошибок. Копирование в NC заняло 9,36 мс (224539 тиков / 24 МГц), около 1,6% от 589 мс
передачи LCD. Устранение
копирования само по себе не объясняет все накладные расходы.

Эксперимент WFE сравнивает WFE OFF/drain 0, OFF/200 и ON/200 при одинаковой
нагрузке. Таймер PPI27 сохраняет возможность проверки тайм-аутов;
снижение уступок CPU требует проверки отзывчивости UART и клавиатуры.
Вариант WFE ON не подтверждён совместным тестом 04.11.

`LEXXOS_RK3506_PMU_PROFILING=ON` — отдельная диагностика CPU0, обычно вместе
с SD diagnostics. `pmu_probe.S` перехватывает только две известные инструкции
проверки CP15; отказ возвращается как `denied`, посторонняя Undefined
Instruction остаётся фатальной. Занятый PMU не перехватывается, прежние
счётчики/селектор/PMCR восстанавливаются. Выключенная опция исключает доступ к PMU.

`sd-hw-bench dma-stress [1..16 [event]]` сравнивает 128 секторов с PIO-базой
по FNV1a в режимах опроса и IRQ/WFE. При отказе DMA остаётся выключенным.
Событие PMU `0x08` считает выполненные инструкции; PMCCNTR с PMCR.D=0 —
такты CPU, включая возможные WFE/IRQ. Окно охватывает весь `rawRead()`,
команды, CRC, хеширование и диагностику. Это не измерение загрузки CPU,
энергопотребления или времени сна; переполнение 32-битного счётчика
делает результат недействительным. Тест FAT RW не подтверждает PMU.

### Альтернативная загрузка legacy uImage

Исторический путь использовал модифицированный U-Boot PicoCalc-Lyra,
FAT-раздел, DTB по `0x00063000`, uImage по `0x03000000` и
`bootm 0x03000000 - 0x00063000`. Адреса должны быть свободны по `bdinfo`.
`boot.txt` обрабатывается только загрузчиком, который это поддерживает;
штатный GPT/FIT U-Boot не начинает читать его из-за появления файла.
В заголовке может стоять `os=linux` для выбора протокола передачи управления,
хотя исполняется LexxOS без Linux. Не заменяйте отказ `bootm` прямым `go`.

### Экран и логотип при загрузке: план

Заставка U-Boot уже проверена. Заставка внутри LexxOS — отдельное предложение:
общий `BootSplash` поверх `DisplayDevice`, встроенный RGB565-ресурс и
однократная инициализация LCD. Пока изображением владеет заставка, консоль
не должна очищать экран; передача управления выполняется при готовности shell.
Диагностика продолжает идти в UART, необязательная очередь LCD ограничена.

Ресурс 160×160 RGB565 занимает 51200 байт, полный 320×320 — 204800 байт DDR.
Возможны палитра/RLE с построчным буфером. Начать можно с синхронного вывода
без зависимости от DMA/SD. Перед регистрацией LCD выполняется проверка IRQ
на 500 мс, задержки панели составляют около 460 мс; это не замер полной
загрузки. Для раннего вывода нужно перенести подготовку дисплея, сохранив
готовность GPIO/SPI/таймера и обязательные задержки панели.

Точки интеграции: `composition/detail/rk3506_device_providers.cpp`,
`app/runtime.cpp`, `devices/display/ili9488_display.cpp`,
`app/detail/picocalc_lcd_console_renderer.cpp`. Проверить ориентацию,
RGB/BGR, инверсию, подсветку, переход к консоли и SWD-перезапуск; не добавлять
искусственную задержку готового интерфейса. При ошибке LCD продолжать через UART.

Смежные документы: [интеграция FreeRTOS](../rk3506-freertos-integration-plan.md),
[план ARMv7-A IRQ/DMA](../armv7a-irq-dma-kernel-roadmap.md),
[прошивка STM32 PicoCalc](../picocalc-jcs-keyboard-firmware.md),
[раскладка клавиатуры](../picocalc-keyboard-layout.md).

## Источники аппаратных сведений

Распиновка и аппаратные параметры в прежних материалах опирались на:

- DTS `base/kernel-6.1/arch/arm/boot/dts/picocalc-rk3506g-luckfox-lyra.dts`
  проекта benklop/picocalc-luckfox-lyra и `rk3502.dtsi` Rockchip Linux;
- [RK3506 TRM v1.2, часть 1](https://rockchip.fr/Rockchip%20RK3506%20TRM%20V1.2%20Part1.pdf),
  главы CRU, IOC, RM_IO, I2C и DMAC;
- [драйвер тактирования RK3506 в Linux](https://github.com/torvalds/linux/blob/master/drivers/clk/rockchip/clk-rk3506.c);
- [PicoCalc-Lyra](https://github.com/sunslayr/PicoCalc-Lyra) — альтернативный
  U-Boot и `boot.txt`;
- [документацию Raspberry Pi Debug Probe](https://www.raspberrypi.com/documentation/microcontrollers/debug-probe.html)
  и [пример OpenOCD для Cortex-A7 RK3506](https://www.taterli.com/10929).

При редакционном объединении новые аппаратные измерения не проводились.
