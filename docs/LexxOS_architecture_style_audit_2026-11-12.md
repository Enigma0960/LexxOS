**Дата:** 12 ноября 2026 г.\
**Аудируемый снимок:** исходники от 11 ноября 2026 г.\
**Тип проверки:** статический архитектурный аудит дерева репозитория, документации и приоритетной выборки исходников.
При исходном аудите сборка, clang-format, clang-tidy, CTest и аппаратные испытания **не выполнялись**.

**Актуализация списка:** 18 ноября 2026 г. По текущему рабочему дереву удалены проверенные закрытые
замечания; номера оставшихся пунктов сохранены. Остальные архитектурные рекомендации требуют отдельной
проверки и не считаются закрытыми по результатам локального стилевого прохода.

Закрытие пунктов 5, 6, 9, 14, 24, 25 и 42, ограничения и host-проверки описаны в

## 1. Итоговая оценка

**Состояние: целевая архитектура уже сформирована на уровне основных подсистем, но миграция границ владения,
платформенных зависимостей и жизненного цикла не завершена.** Переписывать проект целиком не нужно. Наибольший остаток —
не в именовании каталогов, а в зависимостях между слоями и количестве process-global адаптеров.

| Область                                                    | Состояние относительно документации                | Основное препятствие                                                                                       |
|------------------------------------------------------------|----------------------------------------------------|------------------------------------------------------------------------------------------------------------|
| Структура каталогов и выделение подсистем                  | В основном реализовано                             | Некоторые крупные реализации по-прежнему соединяют несколько независимых обязанностей                      |
| Явные `PlatformServices`, composition, `DeviceManager`     | Частично реализовано                               | Сохраняются центральные feature/platform развилки, ручной binding и зависимости от глобального окружения   |
| Изоляция нескольких экземпляров OS/VFS/input               | Частично реализовано                               | `defaultVfs()`, legacy input adapters, `console_mirror`, глобальные focus/scheduler состояния              |
| Product/board/SoC/transport/protocol                       | Миграция продолжается                              | Универсальный `BoardDescriptor`, legacy wiring, два пути SD SPI, непройденный общий U-Boot/runtime backend |
| IRQ, DMA, FreeRTOS, память                                 | Требуется архитектурная и аппаратная приёмка       | Lifetime, quiesce, ISR/RTOS границы, profile budgets и native bridges                                      |
| `.lexx` runtime, графика и ввод                            | Функционально развито, но не полностью изолировано | VM syscall-обработчики зависят от глобальных console/input/graphics services                               |
| Модульность команд                                         | Регистрация централизована и генерируется          | Целевой `ProgramModule` с target composition ещё не доведён до конечного состояния                         |
| Правило «один самостоятельный класс — одна пара `.h/.cpp`» | Во многих основных API соблюдено                   | Обнаружены крупные локальные классы и нетривиальные header-only реализации, требующие оценки на выделение  |

**Масштаб инвентаризации:** Git tree содержит 3 076 entries; в `src/` — 1 148 файлов, из них **541 `.cpp`** и **595
`.h/.hpp`**. По размеру среди `src/**/*.cpp` имеется 36 файлов от 20 KiB, 14 от 30 KiB и 7 от 40 KiB. Это **не
количество нарушений**: размер исходника в байтах и строках служит только сигналом для ревизии. Детально прочитана
выборка крупных и связующих файлов, указанная в таблицах ниже; полный AST-анализ всех классов/функций и exhaustive style
sweep не проводились.

**Обозначения:** `P0` — блокирует безопасное достижение архитектурных инвариантов; `P1` — высокая связанность либо
нарушение границ ответственности; `P2` — преимущественно декомпозиция/сопровождаемость. Сложность: `S` — локальная,
`M` — межмодульная, `L` — затрагивает несколько платформ/сервисов. Строки таблиц описывают **рекомендации**, а не
зафиксированные runtime-баги: потенциальные гонки требуют тестового подтверждения.

## 5. Отдельно: механический стиль и комментарии

В дополнение к архитектурной норме в репозитории действует [
`.codeunifier.json`](../.codeunifier.json)
и [
`.clang-format`](../.clang-format).
По `.codeunifier.json` активны правила: пустая строка после закрытия блока, группировка `#include`, комментарии закрытия
namespace с полным именем, разделение control blocks, own-header-first, пустые строки внутри namespace и группировка
методов/полей класса. **Массовая проверка выполнения каждого правила не проводилась**; документ не утверждает, что все
файлы нарушают эти правила.

Статический `tools/check_cpp_layout.py`, согласно `docs/development-checks.md`, по умолчанию проверяет отсутствие
file-scope `using namespace` в `.cpp`, **а не** всё правило «один самостоятельный класс — отдельная пара файлов».
Поэтому проходящие layout checks не доказывают завершённую декомпозицию. Для полного стилевого аудита требуется
отдельная проверка всех заголовков и кандидатов из таблицы.

Рекомендация по стратегии: не объединять крупный структурный перенос с новыми возможностями или оптимизацией. Для
каждого изменения сохранять существующие feature flags, регистрируемые команды, ABI `.lexx`, размеры workspaces, способы
восстановления устройства и публичную диагностику. Исходный код менять отдельными небольшими `.diff` файлами;
документацию допускается обновлять напрямую.

## 7. Приёмочные проверки

- **Статические:** `clang-format --dry-run --Werror` (только собственные исходники), CMake source lists для каждого
  профиля, отсутствие прямых `FreeRTOS.h`/SoC includes в переносимом app/runtime API, анализ include graph и duplicate
  singleton ownership.
- **Host/simulator:** `minimal`, `standard` и `full` профили; VFS multi-instance; shell, device registry, `.lexx`,
  resource parser, UI, keyboard input/raw-vs-escape; соответствующие CTest и pytest.
- **Hardware:** Lyra (FreeRTOS/cooperative fallback, IRQ/SD/LCD DMA, MIPI/SPI where applicable), Pico/Pico2, ESP-IDF,
  STM32. Отдельные сценарии cold/warm boot, SD RW/removal/recovery, console focus, app exit/cancel и watchdog/panic.
- **Память/производительность:** замеры `.text/.bss/heap/stack`, DMA NC pool, cache maintenance, кадровой частоты и I/O
  throughput до/после каждого патча. Никакой «стилевой» патч не должен незаметно повышать MCU footprint.
- **Тесты инвариантов:** два экземпляра OS в одном процессе; отсутствие пересечений user input/focus, VFS/mount и event
  buses; остановка DMA до освобождения буфера; lifetime task slot до окончания callback/task.
