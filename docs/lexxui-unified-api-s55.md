# LexxUI — единый прикладной UI API и план развития (S5.5)

**Дата аудита:** 9 ноября 2026 г.

## 1. Цель

Один исходный код пользовательского интерфейса должен работать:

- в **native** C++ программе, зарегистрированной через `ProgramManager` и
  выполняемой `ProgramSupervisor`;
- во внешней программе **`.lexx`**, исполняемой RV32I VM.

Виджеты, фокус, стандартная тема, Unicode-шрифт и рендеринг остаются в ОС.
Приложения передают описания и получают семантические события. Системный
интерфейс не должен зависеть от прямых вызовов VM. Отдельного Qt-подобного
рендерера в каждом `.lexx` нет.

## 2. Что уже есть в ветке

| Компонент                                                             | Состояние до S5.5 |
|-----------------------------------------------------------------------|-------------------|
| `GuestView`, системные обработчики 7 контролов                        | Работают          |
| Объектные `Window`, `Widget`, `Button`, `TextField`, `ListView` и др. | Гостевой SDK      |
| Горизонтальный `Row`, вертикальная компоновка, focus-scroll           | Базовая версия    |
| `MessageBox`: Information/Warning/Error/Question, OK/OK+Cancel        | Работает          |
| `app::program_input`, `ProgramSupervisor` focus                       | Работают          |
| Noto Sans Mono: встроенный bitmap, UTF-8 отображение                  | Частично          |
| Конвертер TTF/OTF (`tools/lexx_font_pack.py`)                         | Генерация `.h`    |
| Native C++ клиент того же SDK                                         | Отсутствовал      |

Текущий v1 ограничен восемью контролами на окно, одним `ListView` до восьми
строк, 31 байтом UTF-8 текста на контрол, простым layout и преимущественно
ASCII-редактированием. Временная модель `GuestView` до S5.5 принадлежала VM.

## 3. Архитектура S5.5

```text
              SAME C++ WIDGETS / APPLICATION LOGIC
                Window, Button, TextField, Row
                            |
                     lexx::ui::Transport
                      /              \
               GuestTransport     NativeTransport
               RV32I syscall     AppContext direct
                      \              /
                         UiService
                     process UiSession
                            |
                GuestView + system control handlers
                            |
               DisplayDevice / program_input
```

`apps/sdk/lexx/ui/transport.h` — контракт без виртуальных методов, RTTI,
`std::function` или аллокаций. Контекст `void*` принадлежит транспорту; **указатели callbacks не пересекают VM ABI**.
Для гостя транспорт использует
прежние операции `syscall_graphics` 6–11. Для native программа передаёт
`NativeTransport` с явным `AppContext`.

`UiService` — единая системная точка `show/update/setItems/showDialog/poll/close`.
Она управляет проверками владельца/фокуса, ресурсной блокировкой дисплея,
отрисовкой и публикацией событий. `UiSession` существует отдельно для
каждого клиента, хранит `GuestView`, владельца и флаг отложенной перерисовки.
Сессия не содержит guest pointers. При завершении клиента транспорт обязан
вызвать `close()`, а VM — завершить сессию до освобождения памяти процесса.

Системный `guest_graphics_mode` остаётся эксклюзивным владельцем одного
интерактивного дисплея. Переход из Text в Graphics и обратно централизован.
В первом срезе S5.5 сервис использует уже существующий `GuestView`;
полноценный многоконный менеджер не реализуется.

### Общий код окна

`apps/ui-demo/shared_ui_demo.h` содержит одинаковые контролы, callbacks и
описание окна для двух видов исполнения. Различаются **только** точки входа:

```cpp
// Гостевая .lexx:
lexxos::ui_demo::Demo demo{lexx::ui::guestTransport};
return demo.run();

// Native:
lexxos::ui::NativeTransport native{context};
lexxos::ui_demo::Demo demo{native.transport()};
return demo.run();
```

Это проверяет реальную совместимость исходников, а не просто визуальное
сходство двух независимо написанных примеров.

## 4. Сборка нативной демонстрации

Фича-флаг: `LEXXOS_FEATURE_UI_NATIVE_DEMO`, **OFF по умолчанию**. Он не
влияет на сборку `ui-demo.lexx`. Для включения требуются `DISPLAY` и
`KEYBOARD`. Запуск: `ui-native-demo` (имя зарегистрированной нативной
программы, `ProgramInterfaceKind::Graphical`, `ForegroundTask`).

Из существующей папки сборки хоста:

```sh
cmake -S . -B build/host-full -DLEXXOS_FEATURE_UI_NATIVE_DEMO=ON
cmake --build build/host-full --target lexxos_sim app-ui-demo -j 12
```

Если проект конфигурируется другим preset, включайте флаг в его
`cacheVariables`. Для отключения укажите `-DLEXXOS_FEATURE_UI_NATIVE_DEMO=OFF`
и переконфигурируйте CMake.

В эмуляторе запустите по очереди:

```text
lexx:/> ui-native-demo
lexx:/> /mnt/sd/lexx/ui-demo.lexx
```

Проверьте: Tab, стрелки, ListView, Slider→ProgressBar, MessageBox, Esc,
возврат текстовой консоли, повторный запуск и отмену Ctrl+C. В обоих
вариантах UI-виджеты и обработчики должны быть одинаковыми.

## 5. Инварианты и границы S5.5

- ABI v1 структур `Control=48`, `Document=420`, `Event=40`, `ListItems=260`,
  `DialogDescriptor=132` **не меняется**.
- Guest транспорт остаётся единственным местом вызова `ecall` для UI SDK.
- Native транспорт не вызывает RV32I runtime и не сохраняет сырые guest адреса.
- Квоты, права ресурсов, фокус и lifetime сессий остаются под контролем ОС.
- В S5.5 используется один активный графический владелец, как в прежнем VM.
- При отсутствии дисплея, фокуса или лицензии на графику операции
  завершаются ошибкой, а не захватывают чужой дисплей.
- Программа не должна выполнять busy loop: транспорт `sleep_ms` использует
  соответствующий планировщик; рендер выполняется по изменениям UI.
- `LEXXOS_FEATURE_UI_NATIVE_DEMO` управляет **только демо**, не сервисом UI.

## 6. Дальнейший план

| Этап      | Задача                                                 | Проверка готовности                                |
|-----------|--------------------------------------------------------|----------------------------------------------------|
| **S5.5**  | Общий API, UiService, UiSession, два транспорта        | Один shared demo в native и .lexx                  |
| **S5.6**  | v2 протокол дерева виджетов, вложенные Row/Column/Grid | Более 8 контролов, несколько вложенных контейнеров |
| **S5.7**  | Text engine, шрифты LXFNT через VFS/ресурсы            | Русский ввод, длинные строки, clipping             |
| **S5.8**  | VirtualListView, TableView, постраничные данные        | Сотни записей без роста постоянного пула           |
| **S5.9**  | Keyboard + touch + mouse, hit testing                  | Один UI работает со всеми устройствами             |
| **S5.10** | Темы, метрики, dirty repaint + scissor                 | Изменение одного контрола без полного repaint      |
| **S5.11** | FilePicker, InputDialog, неблокирующие уведомления     | Стандартные диалоги ОС                             |
| **S6**    | UI в файловом менеджере, настройках, проигрывателе     | Прикладные программы используют единый SDK         |

Для протокола v2 рекомендованы стабильные ID узлов, проверяемый
`CreateWidget/SetProperty/RemoveWidget/SubmitChanges/PollEvent` и согласование
версий/функций. **Не расширять** механически `Document.controls[8]` в v1:
это изменит размер wire-структуры и сломает старые `.lexx`.

## 7. Тестовая стратегия

1. Компиляция общего UI с host C++ `LEXXOS_UI_NATIVE=1` и RV32I `-ffreestanding`.
2. Fake Transport: структура документа, вызовы update/set_items, диалог,
   закрытие, отсутствие утечек виджетов.
3. Системные C++ тесты `GuestView`: layout, фокус, модальность, ввод.
4. Интеграционные прогоны обоих приложений в GUI эмулятора.
5. Повторение на Lyra; мониторинг `jobs`, стека, утечек графического lease,
   корректности сброса при отмене процесса.
6. Сборка с `LEXXOS_FEATURE_UI_NATIVE_DEMO=OFF` должна обходиться без
   кода и регистрации демонстрации.

При интеграции на слабые MCU нужно отдельно измерить SRAM и стек нативной
программы: UI-сервис остаётся собранным, как и прежний `GuestView`, а
профили памяти и число UI-сессий требуют собственных будущих квот.
