# Манифесты внешних программ LexxOS

Исходный manifest.json находится в проекте приложения. При упаковке tools/lexx_pack.py проверяет JSON, автоматически
добавляет UTC-время сборки и помещает метаданные внутрь .lexx. Данные можно прочитать без запуска программы.

Ресурсы объявляются необязательным объектом `resources` (алиас `:/...` → исходный путь). Путь источника может быть
абсолютным либо относительным **к каталогу manifest.json**, а не к текущей рабочей директории:

```json
"resources": {
  ":/img/image.png": "assets/image.png",
  ":/strings/ru.txt": "../../shared/ru.txt"
}
```

Файлы произвольного бинарного формата записываются как есть, без упаковки, шифрования или преобразования. Алиас не может
содержать пустые компоненты пути, `.` или `..`, обратную косую черту или `:` за пределами префикса. Размер алиаса — до
127 байт UTF-8, каждого компонента имени — до 63 байт (в силу ABI `DirectoryEntry.name[64]`); максимум 128 ресурсов.
Алиас файла не может одновременно быть родительским каталогом другого алиаса. При упаковке источники сортируются по
алиасу. Встроенный JSON не содержит абсолютных путей сборочной машины: поле `resources` исключается из него.

В коде гостевого приложения ресурсы доступны существующими SDK-функциями:

```cpp
int fd = lexx::open_read(":/img/image.png");
if (fd >= 0) {
    lexx::FileStat info{};
    if (lexx::stat(":/img/image.png", info) == 0) {
        // info.size_low is the resource size in bytes.
    }
    lexx::uint8_t buffer[256]{};
    int count = static_cast<int>(lexx::read(fd, buffer, sizeof(buffer)));
    // Read as many chunks as necessary; seek(fd, offset) is resource-relative.
    lexx::close(static_cast<lexx::uint32_t>(fd));
}
```

Ресурсы доступны только своему приложению и только для чтения. Capability `storage-read` для них не требуется.
`open_read`, `read`, `seek`, `stat` и `close` поддерживают `:/...`; `list_directory(":/")` и `list_directory(":/img")`
возвращают непосредственных детей, а `stat(":/img")` распознаёт неявно созданную папку. Список отдаётся страницами по
восемь записей с учётом параметра `first_index`. Пустые каталоги явно не хранятся. Открытые ресурсы используют те же
четыре файловых дескриптора, что и обычные файлы.

## Режим ввода приложения

Необязательный объект `input` определяет начальный режим клавиатуры:

```json
"input": {"mode": "events"}
```

- `events`: один `KeyEvent` на нажатие через `lexx::poll_key()`. ОС **не** дублирует
  аппаратные или UART-нажатия в поток `console_input`; ANSI-последовательности
  `ESC [ A` не передаются приложению байтами. `lexx::read_char()` в этом режиме
  возвращает `lexx::no_data`. Рекомендуется для GUI, игр и полноэкранного UI.
- `terminal`: совместимый режим для консольных программ: байты и ANSI-последовательности
  передаются через `read_char()`, а события клавиш остаются доступны. При смешивании
  `poll_key()` и `read_char()` возможно дублирование — терминальным приложениям
  следует выбрать один интерфейс. Если `input` не задан, используется `terminal`.

Во время исполнения `lexx::input::set_mode(lexx::input::Mode::Events)` или
`lexx::input::set_mode(lexx::input::Mode::Terminal)` переключает маршрут ввода
только текущего процесса. `lexx::input::get_mode(mode)` читает значение; для обоих
вызовов нужна capability `keyboard`. При переключении очищаются ожидающие
байты `console_input`, при выходе режим удаляется. Shell всегда сохраняет свою
обработку ANSI; переключение одной программы не меняет другую.

Для экономии RAM упаковщик проверяет `input.mode` и кодирует начальный режим
в `header.flags`, бит `0x00000001` (`events`); значение `terminal` — нулевой бит.
Встроенный JSON сохраняет `input` без изменений. Старые файлы с нулевыми
флагами остаются совместимы с новой ОС; новые файлы с битом требуют ОС,
которая поддерживает этот флаг. Версии формата и RV32I ABI остаются равными 1.

## Пример manifest.json

    {
      "schema": 1,
      "id": "org.example.hello",
      "name": "Hello",
      "version": "1.2.3",
      "description": "Приветствие и проверка терминала",
      "author": "Example Development Team",
      "license": "MIT",
      "contacts": {
        "email": "dev@example.org",
        "website": "https://example.org",
        "repository": "https://example.org/hello.git"
      }
    }

Обязательные поля: schema (целое число 1), id, name, version, author, license (непустые строки).
Необязательные: description (строка), contacts (словарь строк). Версия приложения следует SemVer (MAJOR.MINOR.PATCH и
допустимые suffix).
Идентификатор id должен оставаться постоянным от версии к версии и может содержать латинские буквы, цифры, точки,
дефисы, подчёркивания.

Значение license нужно брать из фактической лицензии приложения (рекомендуется SPDX).
В демонстрационных проектах указано UNLICENSED: это отсутствие публично предоставленной лицензии, а не свободная
лицензия.
Поле build в исходном файле указывать запрещено: его добавляет упаковщик.

## Сборка

    python3 tools/lexx_pack.py app.bin app.lexx --manifest manifest.json --memory 65536 --stack 4096 --cap console,keyboard

Упаковщик автоматически добавит поле с UTC timestamp, например:

    "build": {
      "timestamp": "2026-10-20T00:00:00Z"
    }

Дата выше иллюстрирует формат, а не результат конкретной сборки.
Значение берётся из времени запуска упаковщика. SOURCE_DATE_EPOCH заменяет текущее время для воспроизводимых сборок.
Опция --manifest необязательна: без неё создаётся прежний формат без манифеста.

## Проверка внутри LexxOS

    lexx:/> version
    lexx:/> lexx-info /mnt/sd/apps/hello.lexx
    lexx:/> lexx-info --json /mnt/sd/apps/hello.lexx

Команда version уже показывает версию/дату компиляции самой LexxOS.
lexx-info показывает заголовок выбранной программы (формат, ABI, архитектура, права, память, размер) и полный встроенный
JSON.
--json выводит только JSON, что подходит для экспорта и будущих инструментов управления пакетами.
Старые исполняемые файлы получают сообщение manifest: not present (legacy), --json возвращает ошибку.
Команда ни при каких обстоятельствах не запускает исполняемый код.

## Формат бинарного файла

    +-------------------------------+
    | LEXX header v1 (64 bytes)     |
    +-------------------------------+
    | RV32I executable image        | imageSize из заголовка
    +-------------------------------+
    | raw resource data             | 0..N байт (не входит в imageSize)
    | resource directory            | N переменных записей
    | "LXRS" (4 bytes)              |
    | count (little-endian u32)     |
    | directory length (u32)        |
    | directory CRC-32 (u32)        |
    +-------------------------------+
    | JSON manifest (UTF-8)         | максимум 4096 байт
    +-------------------------------+
    | "LXMF" (4 bytes)              |
    | length (little-endian u32)    |
    | CRC-32 (little-endian u32)    |
    +-------------------------------+

Каждая запись resource directory имеет структуру
`offset: u32, size: u32, aliasLength: u16, aliasUtf8: byte[aliasLength]`; поля в little-endian. Значение `offset` —
абсолютное смещение от начала `.lexx`. CRC-32 охватывает только таблицу, а не содержимое ресурсов. При отсутствии
ресурсов `LXRS` не записывается; при отсутствии манифеста формат старого приложения не изменяется.

Зарезервированные поля заголовка остаются нулями. Header v1 и ABI v1 не изменяются: imageOffset/imageSize по-прежнему
адресуют только машинный код.
Существующий загрузчик уже допускает данные после image и поэтому может исполнять такие файлы без доработки.

lexx-info проверяет размер и положение JSON (только после образа), CRC-32, читает файл частями по 128 байт. В обычном
режиме ниже JSON выводится таблица ресурсов с алиасами, смещениями и размерами; `--json` оставляет только JSON.
Загрузчик и `lexx-info` проверяют контрольную сумму и границы каталога `LXRS` без копирования ресурсов в память VM.
Изменение исходного файла ресурса автоматически вызывает повторную упаковку через CMake DEPENDS.
CRC-32 обнаруживает случайные повреждения, **но не подтверждает подлинность автора** и не является цифровой подписью.
