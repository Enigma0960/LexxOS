# LexxOS v2 — план расширения SDK для графических приложений `.lexx`

> **Статус:** проект технического плана (RFC / roadmap)\
> **Дата:** 2026-11-03\
> **Целевая линия разработки:** новая архитектура, версия 2\
> **Статус реализации:** данный документ описывает *планируемые* изменения; исходный код SDK и ядра ОС не изменён.

## 1. Назначение и принципы

Цель — обеспечить создание полноценных **графических исполняемых приложений `.lexx`**, выполняющихся в текущей
переносимой RV32I VM LexxOS. SDK предоставляет общие интерфейсы для графических приложений.

Платформы для проверки:

- **Основная:** PicoCalc / Luckfox Lyra M (RK3506, дисплей ILI9488 320×320, RGB565, клавиатура, FreeRTOS).
- **Обязательная для автоматических проверок:** host/emulator LexxOS без физического устройства.
- **Контроль переносимости:** RP2040/RP2350 и другие платы с `DisplayDevice` — с аппаратными ограничениями, без
  требования поддерживать все функции сразу.

Основные решения:

1. Сохранять `.lexx` как архитектурно независимый переносимый исполняемый файл; не добавлять прямого доступа гостя к
   MMIO, DMA, адресам физических буферов и системным C++-объектам.
2. **Гость отправляет команды рисования, ОС рисует.** Попиксельные циклы, текстовый растеризатор, декодер спрайтов и
   кадровая синхронизация выполняются в нативных сервисах LexxOS.
3. Использовать существующие `DisplayDevice`, presenter, `ProgramSupervisor`, систему capabilities, VFS и упаковку
   ресурсов `.lexx`. Не создавать отдельный драйвер дисплея «для игр».
4. Каждый ресурс принадлежит конкретному процессу/сеансу. При штатном выходе, Ctrl+C, `stop`, ошибке VM и неуспешном
   запуске он освобождается автоматически.
5. Сохранять ABI-совместимость со старыми `.lexx`: расширять API добавлением функций и capabilities; изменение формата
   исполняемого файла допускается только при доказанной необходимости и с отдельным планом миграции.
6. Делать небольшие, независимые и проверяемые патчи. Для каждого этапа предоставлять **один общий `.diff`**;
   документацию допускается поддерживать отдельно.

## 3. Целевая архитектура

```text
+-----------------------------------------------------------+
| Application: game.lexx                                    |
| game state / UI layout / assets aliases / input handling  |
+------------------------------+----------------------------+
                               | lexx SDK API (RV32I)
                               v
+-----------------------------------------------------------+
| Guest graphics.h / resources.h / input.h / time.h          |
| Stable structs, handles, status codes, bounded command     |
| buffer; syscall wrappers                                   |
+------------------------------+----------------------------+
                               | ECALL, copy/validate
                               v
+-----------------------------------------------------------+
| LexxOS process services                                    |
| GraphicsSessionManager   ResourceService   InputRouter    |
| ClockService             AppStorage         ProcessMemory |
+------------------------------+----------------------------+
                               | native calls
                               v
+-----------------------------------------------------------+
| GraphicsRenderer                                           |
| clip, rect, text, sprite, dirty rects, resource cache      |
+------------------------------+----------------------------+
                               v
+-----------------------------------------------------------+
| DisplayDevice / DoubleBufferedDisplay / presenter / DMA    |
| host emulator or RK3506 / RP2040 / other board backend     |
+-----------------------------------------------------------+
```

**Границы ответственности:**

- **SDK:** стабильные C-compatible структуры и безопасные C++-обёртки, не зависящие от хостовой платформы.
- **VM:** права, проверка указателей/диапазонов/длин, владение handles и ресурсов, правила отказа.
- **GraphicsService:** сеансы и операции сцены, ресурсы и кэш, текст/спрайты, контроль частоты и очередей.
- **DisplayDevice:** только аппаратно-независимый вывод подготовленных прямоугольников/кадров.
- **Приложение:** модель игры, переходы между экранами, композиция сцены, выбор спрайтов; никакого SPI, DMA или прямого
  framebuffer.

## 5. S0 — технический аудит и спецификация ABI

### Задачи

- [ ] Установить фактический HEAD ветки новой архитектуры v2 и список изменённых SDK/VM/Display/Program API.
- [ ] Подтвердить доступность `Graphical`-фокуса в v2 и реальное поведение консоли во время работы полноэкранного
  приложения.
- [ ] Проверить, какие подсистемы собираются условно (`LEXXOS_FEATURE_DISPLAY` и родственные feature flags), и какие
  устройства не имеют дисплея.
- [ ] Зафиксировать registry системных вызовов: на дату проверки заняты номера **0–24**;
  перед выделением новых номеров повторно сверить текущий реестр ABI.
- [ ] Определить новые capability-биты, версию функций и способ определения поддержки во время выполнения
  (`query_features` или аналог существующего API).
- [ ] Составить ABI layout-тесты (`sizeof`, `alignof`, `offsetof`) и сопоставить guest/host little-endian представление.
- [ ] Добавить файл спецификации, например `docs/external-programs-graphics-abi.md`, с ошибками и гарантиями.

### Контракт ABI

- Только **фиксированные размеры** `uint8_t`, `uint16_t`, `uint32_t`, `int32_t`; для времени — два `uint32_t` либо
  `uint64_t` с явно закреплённым layout.
- Не передавать `size_t`, `bool`, host pointers, `std::string`, виртуальные C++-классы через ABI.
- Каждая структура содержит `size`/`version`, `reserved` должны быть нулевыми. Неизвестные версии и команды отклонять
  без частичного эффекта.
- Вызовы должны возвращать единые различимые состояния: `Ok`, `Unsupported`, `PermissionDenied`, `Busy`,
  `InvalidArgument`, `OutOfMemory`, `InvalidHandle`, `IoError`, `Cancelled`, `Timeout`.
- Новая capability `graphics` обязательна для отрисовки; наличие дисплея определяется runtime-проверкой, а не только
  флагом сборки.
- Договориться, допускается ли работа graphical app только в foreground (рекомендация для первой версии: **только
  foreground**).

**DoD S0:** существует согласованная спецификация, определены тестируемые ABI-структуры, legacy-приложения не требуют
пересборки для запуска.

## 6. S1 — Менеджер графических сессий

### Минимальные операции

```cpp
// Эскиз будущего SDK, не существующие сейчас сигнатуры.
namespace lexx::graphics {
    enum class Status : int32_t;
    struct DisplayInfo;
    Status open(DisplayInfo& outInfo, uint32_t& outSession);
    Status close(uint32_t session);
    Status begin_frame(uint32_t session);
    Status submit(uint32_t session, void const* commands, uint32_t size);
    Status end_frame(uint32_t session);
}
```

Рекомендации:

1. **Один активный полноэкранный владелец дисплея**. Ownership идентифицируется не только integer-handle, но и
   процессом/инстансом VM; идентификатор другого процесса нельзя использовать даже при угадывании значения.
2. `open()` атомарно проверяет capability, foreground focus, доступность и память. При ошибке состояние ОС не меняется.
3. После успешного `open()` console presenter не перезаписывает графический экран. UART-журнал продолжает работать
   независимо от LCD, если он включён.
4. `end_frame()` отправляет подготовленный кадр существующему presenter; не занимается бесконтрольным busy-loop
   ожиданием DMA.
5. `close()` возвращает управление консольному слою и инициирует полную перерисовку shell, а не предполагает сохранность
   прежнего буфера.
6. Завершение процесса, fault, Ctrl+C, `stop`, переключение фокуса или неуспешный запуск вызывают **один идемпотентный
   cleanup**. Нельзя передавать гостю владение framebuffer или DMA-дескрипторами.
7. Если кадр ещё передаётся DMA, ресурсы освобождаются только после безопасного завершения/отмены передачи или
   отключения ссылки со стороны presenter.
8. Повторный вызов `close()`, незакрытый кадр, неправильный session handle дают предсказуемый статус, без краха ОС.

**DoD S1:** последовательность `launch → acquire → draw → Ctrl+C/stop/fault → console → relaunch` повторяется 100 раз в
host-тесте без потерь ресурсов, deadlock и повреждений shell.

## 7. S2 — Graphics ABI и пакетный рендеринг

### Набор обязательных команд v1

| Команда                   | Назначение                | Примечание                                  |
|---------------------------|---------------------------|---------------------------------------------|
| `CLEAR`                   | Заливка области/экрана    | RGB565                                      |
| `FILL_RECT`               | Заполненный прямоугольник | Clipping в host                             |
| `STROKE_RECT`             | Контур                    | Толщина 1 для MVP                           |
| `LINE`                    | Линия                     | Не обязательно для первой демоверсии        |
| `TEXT`                    | Вывод строки              | Базовый встроенный bitmap-font; лимит длины |
| `SPRITE`                  | Вывод спрайта             | Реализуется после S3                        |
| `SET_CLIP` / `RESET_CLIP` | Ограничение области       | Защита от выхода за экран                   |

### Формат пакета

Использовать одно или небольшое число `ecall` на кадр, а не системный вызов на каждый пиксель. Первоначальные лимиты для
обсуждения: **до 4 КиБ на submit**, **до 128 команд в пакете** и **не более одного незавершённого кадра на сеанс**. Эти
числа — проектные, они должны быть проверены на v2 и могут задаваться профилем платформы.

```text
Guest VM                   LexxOS host                  Display
   | batch(ptr,len)           |                          |
   +------------------------->| validate guest range     |
   |                          | copy bounded command buf |
   |                          | validate ALL commands    |
   |                          | clip and render          |
   |                          |----dirty rectangles----->|
   |<--status-----------------|                          |
```

Критически важные правила:

- Нельзя сохранять raw guest pointers после возврата `ecall`.
- Перед исполнением проверять `pointer + length` **без integer overflow**, доступ к гостевой памяти, alignment, границы
  каждого command payload, координаты и допустимые ресурсы.
- Для операций с пакетом предпочтительна модель **«полная валидация → исполнение»**: неверная вторая команда не должна
  оставлять частично выполненный набор.
- Для текста передавать длину явно; не читать бесконечно NUL-terminated строку из гостевой памяти.
- Координаты signed 32-bit, размер и clipping проверять с расширенной арифметикой, исключая переполнение `x + width`.
- Не допускать вложенных `begin_frame`, скрытой блокировки без timeout и неограниченного накопления кадров.
- Guest не выбирает аппаратный SPI/I2C, частоту, DMA-адреса, power/backlight и не вызывает hardware-present напрямую.
- Ресурсы вне видимой области не должны вызывать физические обращения или создавать отрицательные размеры
  прямоугольников.

### Особенности PicoCalc

Для 320×320 RGB565 один кадр занимает **204 800 байт** (200 КиБ), два кадра — **409 600 байт** (400 КиБ). Нельзя
требовать guest framebuffer, тем более при лимите 64 КиБ. Предполагается переиспользовать системный буфер/presenter и
отображать изменённые прямоугольники. Частичные обновления возможны только в границах семантики `DisplayDevice`
/конкретного backend и требуют проверки на «остаточные» пиксели.

**DoD S2:** отдельная `graphics_demo.lexx` выводит фон, 100 прямоугольников, строку, а затем анимирует прямоугольник;
host golden-image тест сравнивает пиксели и проверяет clipping.

## 8. S3 — Отрисовка спрайтов и ресурсов

### Исходная база

В просмотренной версии `.lexx` уже поддерживает встроенные ресурсы с алиасами `:/...`, доступ по `open_read/read/seek`,
до **128 resource entries** и ресурсы вне образа VM. Упаковка выполняется `tools/lexx_pack.py`. **Не добавлять вторую
систему ресурсо-упаковки**, пока существующая не исчерпана.

### Предлагаемый API

```cpp
// Эскиз. Названия и бинарный ABI уточняются на S0.
namespace lexx::resources {
    Status open_sprite(char const* alias, uint32_t& outHandle);
    Status get_sprite_info(uint32_t handle, SpriteInfo& outInfo);
    Status close_sprite(uint32_t handle);
}
// Команда SPRITE передаёт spriteHandle, frameIndex, x, y и параметры вывода.
```

### Форматы и загрузка

- Для MVP: компактный **версионированный sprite-pack** с little-endian таблицей offset/size, геометрией, pixel format
  RGB565 или индексированным форматом с палитрой, количеством кадров, прозрачным цветом. Это **предложение**, не
  утверждение о существовании такого формата.
- PNG/JPEG допускаются только на этапе build-time conversion. Runtime-декодер тяжёлых форматов не включать в MVP.
- Host сам читает данные ресурса через VFS по *проверенному alias приложения*: не разрешать произвольный absolute path и
  выход за пределы payload.
- Ограничить число открытых sprite-handles, размеры кадров, cache bytes и maximum pixels до выделения памяти.
- На повреждённом offset, размере, CRC, сжатом блоке или неожиданном EOF возвращать ошибку. В идеале добавить **CRC
  содержимого** в формат sprite-pack: текущий CRC resource table сам payload не защищает.
- Кэш ограничен профилем платформы, вытеснение LRU/FIFO допустимо. Сохранять frame metadata отдельно от пиксельных
  данных.
- Поддерживать композицию с clipping и простым transparent color-key; alpha blending оставить опцией P2.

### Формат ресурсов приложения

```json
{
  "schema": 1,
  "id": "org.lexxos.apps.sprite_demo",
  "name": "Sprite Demo",
  "version": "0.1.0",
  "author": "LexxOS Contributors",
  "license": "TO_BE_VERIFIED",
  "resources": {
    ":/sprites/starter.pak": "assets/starter.pak",
    ":/data/frames.bin": "assets/frames.bin",
    ":/ui/icons.bin": "assets/icons.bin"
  }
}
```

`license` здесь **заглушка**: при реализации заменить на подтверждённую лицензию соответствующих исходников/ресурсов.

**DoD S3:** демо с анимированным 2–4-кадровым спрайтом; повреждённый pack/alias не приводит к out-of-bounds или
зависанию, повторный вход не оставляет открытых handles.

  ограниченным размером и ошибками; не путать его с `ProgramMemoryArena` на стороне ОС.
- [ ] Проверить alignment, integer overflow, OOM, back-to-back launches, параллельные процессы и очистку.
- [ ] Вывести в `lexx-info` memory request / max allowed / stack / estimated heap, а в `jobs` — фактическую резервацию и
  результат отказа, где это доступно.

**Важно:** увеличение `memorySize` само по себе не ускорит RV32I VM. Потребуются измерения cost per instruction,
syscalls, кэша, DDR и pipeline рисования; не следует автоматически переносить **все** спрайты в guest RAM.

**DoD S4:** при каждой поддерживаемой конфигурации приложение либо запускается с корректной разметкой памяти, либо
отказывается *до исполнения* с объяснением объёма; проверка OOB всегда останавливает гостя, а не ОС.

## 10. S5 — API времени и RTC

### Будущий контракт

```cpp
namespace lexx::time {
    struct UtcTime {
        uint32_t seconds_lo;
        uint32_t seconds_hi;
        uint32_t flags;      // valid, source RTC, source software, synchronized
    };
    Status get_utc(UtcTime& result);
    uint32_t monotonic_milliseconds();
}
```

- Монотонные миллисекунды уже существуют, но 32-битное значение переполняется примерно через **49,7 суток**. Для
  интервалов использовать unsigned delta или расширенный monotonic clock.
- RTC предоставляет **UTC**, не local time; часовой пояс — ответственность приложения/UI.
- Возвращать статус `NotReady`/флаг невалидного источника, если время не установлено или программные часы недостоверны
  после перезагрузки.
- Доступ к аппаратному RTC — только через сервис ОС; приложению не требуется `devices` или прямой I2C.

**DoD S5:** unit-тесты для leap day, перехода года, неточного RTC, смены времени назад, cold boot и отсутствия чипа;
игровой пример не делает вид, что прошло время, если timestamp недостоверен.

## 11. S6 — постоянное хранилище приложения

### Предлагаемые операции

```cpp
namespace lexx::storage {
    Status read_app_data(char const* name, void* out,
                         uint32_t capacity, uint32_t& actualSize);
    Status write_app_data(char const* name,
                          void const* data, uint32_t size);
}
```

Требования:

1. Пространство имён формировать внутри ОС по **проверенному `manifest.id`**, например логический ключ
   `app-id + save-name`; приложение не задаёт произвольные host-пути и не может читать чужие сохранения.
2. Приложение видит различимые результаты `Ok`, `NotFound`, `ReadOnly`, `NoSpace`, `PermissionDenied`, `Corrupt`,
   `IoError`, `Unsupported`.
3. Ограничить имя (без `..`, `/`, `\\`, NUL внутри), максимальный размер записи и совокупную квоту из runtime profile.
4. Разработать независимую от носителя запись с версией payload, generation number и CRC32. Для питания без UPS
   использовать **двухслотовый** протокол: писать в неактивный слот, проверять данные, затем выбирать наиболее новое
   полностью валидное поколение.
5. Отдельно определить гарантии flush/fsync/rename конкретного VFS/backend: CRC и две копии уменьшают риск потери
   прогресса, но **не заменяют гарантии атомарности и сброса на носитель**.
6. На PicoCalc SD сейчас может быть смонтирована read-only: **никаких ложных успешных сохранений**. До появления
   writable backend MVP должен работать без persistence либо с явно обозначенным временным режимом.
7. Можно добавить storage capability `app-data` отдельно от unrestricted `storage-write`; согласовать с политикой
   безопасности/ABI v2.

**DoD S6:** сохранение и восстановление между запусками, проверка повреждённого/неполного слота, отсутствие доступа к
данным другого `manifest.id`, корректные ошибки read-only/no-space.

## 12. S7 — ввод, жизненный цикл и диагностика

### InputRouter

- Все клавиатурные источники, включая PicoCalc/JCS, host keyboard и UART fallback, доставлять через единый event router
  с контролем foreground focus.
- На graphical focus события принадлежат игре; shell не должен одновременно реагировать на клавиши управления меню
  (кроме системной команды отмены/управления фокусом).
- Различать `KeyDown`, `KeyUp`, repeat (если поддерживается), modifiers и scan code. Сообщать о переполнении очереди или
  заданном drop policy.
- При смене фокуса очищать/переинициализировать состояние зажатых клавиш, чтобы не возникали «вечные» нажатия.
- Обработка Ctrl+C/stop должна происходить независимо от состояния `begin_frame` и наличия ресурса, если VM продолжает
  исполняться и выполняет точки отмены.

### Диагностика

Добавить счётчики, доступные из shell или benchmark-подсистемы:

- `graphics.sessions`: активный владелец/фокус, число ошибочных открытий и forced cleanup;
- `graphics.frame`: submitted/presented/dropped, avg/p95 frame time, ограничение очереди;
- `graphics.render`: количество команд, clipping, dirty rectangles, decode/cache hits/misses;
- `vm`: инструкции, ECALL count/cost, idle/yield, CPU usage по имеющимся счётчикам;
- `memory`: лимиты, peak guest heap, renderer cache, page/stack failures.

Для более слабых устройств диагностика должна быть опциональной (`LEXXOS_FEATURE_GRAPHICS_DIAGNOSTICS` или аналог в v2)
и не мешать базовому исполнению.

**DoD S7:** графические приложения проходят foreground/background/focus/stop тесты, клавиши не дублируются, консоль
корректно возвращается, длительные кадры не блокируют UART-сессию.

## 13. S8 — дальнейшее развитие (не блокирует MVP)

### Аудио

- Неблокирующий `play_effect(resource_id, volume)` с ограниченной очередью и политикой смешивания.
- Загрузка коротких эффектов из ресурсов вместо непосредственной работы guest с аудиоустройством.
- Возможность отключения audio на платах без backend (graceful degrade).

### Графика

- Sprite flip/scale, text alignment, UTF-8 с согласованным ограниченным набором glyphs, прозрачность/alpha — после
  измерения стоимости.
- Системный анимационный helper (frame index по monotonic time), но игровые сценарии остаются в приложении.
- Dirty-region merging с лимитом на количество прямоугольников, дублирование/уплотнение кадров, frame pacing, optional
  vsync/flush semantics если поддерживает backend.

### Виртуальная машина

- Раздельно бенчмаркать opcode classes, switch dispatch, memory access, syscalls, bursts команд рендера и вызовы
  ресурсов.
- Не объединять оптимизации VM с разработкой ABI: сначала baseline, затем отдельные маленькие патчи с измерениями на
  RK3506 и host.
- Рассматривать RV32IM, JIT или native ARM `.lexx` **только как отдельное архитектурное решение** после доказанного
  узкого места и оценки переносимости/безопасности; не требуются для первого graphics SDK.

## 15. Тестирование и критерии производительности

### 15.1. Обязательные тесты

| Тип          | Проверка                                                                               | Среда                      |
|--------------|----------------------------------------------------------------------------------------|----------------------------|
| ABI          | структура, версия, неверные указатели, переполнения, неизвестная команда               | host CI                    |
| Растеризатор | точность пикселей прямоугольников/текста/обрезки, объединение изменённых областей      | host pixel/golden          |
| Security     | Capability denied, чужой session/resource handle, alias traversal                      | host/VM                    |
| Ресурсы      | обрезанный пакет, неверные смещения, огромные размеры, повторная загрузка/освобождение | host fuzz + VM             |
| Lifecycle    | launch/stop/Ctrl+C/VM fault, 100–1000 циклов cleanup                                   | host + Lyra                |
| Память       | 64/128/256/512 КиБ, нехватка памяти, пересечение стека, выход за границы               | host + supported HW        |
| RTC          | Невалидное время, rollover, time reversal, offline progress                            | host                       |
| Storage      | RO VFS, interrupted write, two-slot recovery, isolation                                | host + Lyra при наличии RW |
| Ввод         | фокус, нажатие/отпускание, залипание клавиши, отмена, переполнение очереди             | host + PicoCalc            |
| Интеграция   | `graphics_demo.lexx`, `sprite_demo.lexx`                                 | host + Lyra                |
| Regressions  | shell help, LCD scroll, SD read, audio, старые `.lexx`                                 | host + Lyra                |

### 15.2. Предварительные целевые показатели (не гарантии)

- **MVP:** 10–15 видимых FPS для небольшой 2D-сцены с частичными обновлениями, в допустимой нагрузке CPU.
- **Ввод:** задержка реакции интерфейса p95 менее 100 мс при типичной игровой сцене.
- **Рендеринг:** нулевая динамическая аллокация *на каждую простую команду* в горячем пути; общий cache имеет жёсткий
  лимит.
- **VM:** количество `ecall` на кадр измеряется и сокращается батчингом; отдельный отчёт по инструкциям и стоимости
  syscall.
- **Надёжность:** после 100 повторных запусков нет роста занятой памяти/handles, а shell и UART остаются работоспособны.

Эти показатели уточняются только после baseline-замеров **на реальной Lyra**, особенно с учётом уже измеренной стоимости
передачи полного кадра SPI. Из теста `display-test` нельзя автоматически выводить игровую FPS: там могут отличаться
области обновления, рисование, VM и декодирование.

### 15.3. Минимальные измерения на Lyra

```text
Scenario A: clear + 10 rects + text (static scene)
Scenario B: 1 moving sprite, partial invalidation
Scenario C: 10 sprites, 4 animation frames, changed ROI
Scenario D: 100 UI rects, batch vs individual ecall baseline
Scenario E: resource-pack streaming/cache cold vs warm
Scenario F: start / stop / relaunch repeated
```

Для каждого сценария фиксировать VM instructions, render-us, wait/present-us, bytes transmitted, dropped frames, guest
RAM peak, native cache peak и CPU idle/yield. Результаты хранить в versioned benchmark-отчётах.

## 18. Рекомендованный первый шаг

**Порядок первых изменений в коде — `GFX-00` → `GFX-01` → `GFX-02`.**

Практически:

1. Сверить этот документ с реальной веткой v2 и исправить фактическое имя ветки/пути/номера вызовов.
2. Закрепить интерфейс сессии, сообщения об ошибках, ownership и правила cleanup.
3. Сделать host-level `GraphicsService` и маленькое `.lexx`-демо без внешних ресурсов.
4. Добиться гарантированного возврата shell после Ctrl+C, VM fault и повторного запуска.
5. Только затем добавить спрайтовый pack и начать визуальный порт игры.

**Результат первой итерации:** переносимый `.lexx` может получить экран, пакетно нарисовать фон/примитивы/текст,
обработать ввод и безопасно завершиться. Это даёт основу для файлового менеджера, системного UI и игр.

## Приложение A. Изменения, сознательно не включённые в MVP

- Нативный ARM-бинарный формат или JIT-компилятор для `.lexx`.
- Произвольный доступ приложений к SPI, DMA, LCD-регистрам или физическому framebuffer.
- Полноценный многоконный GUI/композитор, drag-and-drop и сложная система виджетов.
- Декодирование PNG/JPEG/GIF в гостевой VM.
- Изменение политики безопасности устройства ради одного приложения.

## Приложение B. Решения, которые нужно принять на S0

1. **Актуальность плана.** Перед изменениями сверить уже реализованные возможности SDK и VM.
2. **Syscall allocation:** новый диспетчер команд одним номером или отдельные `open/submit/close`? Рекомендация:
   небольшой набор сервисных вызовов и один пакетный `submit`.
3. **Политика отображения:** только fullscreen exclusive в v1 или сразу overlay? Рекомендация: fullscreen exclusive.
4. **Ресурсный формат:** конвертация внешнего формата спрайтов либо его декодирование во время выполнения. Рекомендация:
   конвертер в build-time format.
5. **Максимальная guest RAM:** плата задаёт верхний предел; 512 КиБ — целевой тест для Lyra, не общий обязательный
   минимум.
6. **Writable backend:** какой носитель гарантированно поддерживает запись на PicoCalc Lyra? До ответа storage API не
   объявлять durable.
7. **Наличие готового compositor в v2:** адаптироваться к существующему сервису, если он уже реализован.
