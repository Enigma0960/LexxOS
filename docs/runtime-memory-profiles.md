# Профили памяти среды выполнения LexxOS

`src/lexxos/runtime/runtime_profile.h` содержит переносимые типы лимитов и
`validateRuntimeProfile`; он не включает профили платформ. Подсистемы получают
`standardRuntimeProfile` через `src/lexxos/runtime/selected_runtime_profile.h`,
в том числе для `constexpr` размеров массивов. CMake выбирает слои для каждой
цели и генерирует `memory-profiles/<target>/lexxos_target_memory_profile.h`.
Настройки накладываются в C++ без динамического выделения памяти; загрузчик
и карта DDR при этом не меняются.

Порядок применения:

1. `RuntimeProfile{}` — переносимые значения по умолчанию.
2. `config/memory/chips/<chip>.h` — бюджет памяти чипа.
3. `config/memory/platforms/<platform>.h` — ограничения планировщика и платформы.
4. `config/memory/boards/<board>.h` — итоговые настройки платы/продукта.

`lexxos_attach_memory_profile(target CHIP ... PLATFORM ... [BOARD ...])` в
`config/cmake/MemoryProfiles.cmake` проверяет совместимость слоёв и задаёт
приватные include paths и `LEXXOS_RUNTIME_PROFILE_HEADER` только этой цели.
Ошибочные пары chip/platform и неподходящий board отклоняются при configure.
Итоговые числовые ограничения проверяет `static_assert` при компиляции.
Отдельные host-инструменты без выбранного профиля используют базовые значения.
Старые `LEXXOS_MEMORY_*` остаются для SDK heap-конфигурации и контрактных проверок;
они больше не выбирают слои внутри общих C++ заголовков.

`minimal`, `standard`, `full` выбирают состав функций и команд. В текущих
настройках они используют одинаковые лимиты памяти данной платы; этот перенос
не уменьшает бюджеты `minimal` и не увеличивает бюджеты `full`. Числовой снимок
host-матрицы и SDK/Lyra-профилей приведён в
[отчёте профилей от 18.11.2026](runtime-memory-report-2026-11-18.md).

Лимит `profile.ui.maxResolvedControls` относится к тому же профилю. Он
определяет размер массива вычисленных UI-контролов в `GuestView` и
отображается командой `mem profile`.

Базовое значение — 32, платформа Pico использует 12, PicoCalc Pico 2 W —
16, PicoCalc Lyra — 64. Отдельное поле `profile.ui.maxTreeNodes`
ограничивает число узлов дерева, включая контейнеры. Для Pico оно равно
16, для Lyra — 64, базовое — 32. Лимиты должны удовлетворять
`8 <= maxResolvedControls <= maxTreeNodes <= 256`. Протокол v2
остаётся фиксированным на 16 узлах, а v3 передаёт только используемые
узлы и проверяет пределы платы.
Для изменения на конкретной плате задайте
`profile.ui.maxResolvedControls` в `config/memory/boards/<board>.h`,
без нового CMake-флага.

Для `picocalc_lyra` три слоя выбирает `config/cmake/platforms/rk3506_bringup.cmake`
на цели исполняемого файла RK3506, включая сборку без shell. Все единицы
трансляции получают одинаковые определения. Новое сочетание подключается
к соответствующей цели прошивки, а не глобально ко всем сборкам и тестам.

## Профили SDK RP2040/RP2350 и ESP-IDF

`config/cmake/MemoryProfiles.cmake` задаёт настройки цели Pico и компонента
LexxOS для ESP-IDF. Чип выбирается по `PICO_PLATFORM` (`rp2040`, `rp2350-arm-s`)
или `IDF_TARGET` (`esp32`, `esp32s3`, `esp32p4`), а не по предположению из
имени платы. Псевдонимы платы используют один профиль чипа. Цель получает
каталог включения `config/`.

Слой чипа обозначает выбранную цель, не выдумывая фиксированный размер кучи.
В Pico FreeRTOS бюджет `heap_4` берётся из `config/memory/pico_freertos_heap.h`
как для `FreeRTOSConfig.h`, так и для `RuntimeProfile`: по умолчанию
126 КиБ у RP2040 и 224 КиБ у RP2350. `LEXXOS_PICO_FREERTOS_HEAP_KB`
сохраняет настройки конкретного preset; ограничение CMake 88 КиБ для
PicoCalc первого поколения остаётся. `mem profile` показывает тот же
эффективный бюджет, а не свободную SRAM или текущее число выделений.

В Pico без FreeRTOS и в ESP-IDF `kernel.heapBytes == 0`: фиксированной
кучей LexxOS эти сборки не владеют. ESP-IDF управляет собственной кучей
и выделением задач. Ноль в профиле не означает отсутствие физической RAM.
Стеки, очереди и управляемые рабочие области программ Pico FreeRTOS
выделяются из одной арены `heap_4`; `kernel.taskStackPoolBytes` равен нулю,
чтобы не учитывать один резерв дважды.

Для LCD-консоли ESP-IDF сохраняется стек зеркалирования 8192 байта у
Cardputer и JC ESP32-P4, 4096 у M5Stack Basic. У RP2350 PicoCalc — 8192,
у RP2040 PicoCalc и остальных Pico — 4096. Другие лимиты shell, программ
и очередей сохраняют переносимые значения до обоснованного измерениями
изменения. `mem profile` показывает чип, платформу и плату, чтобы ошибку
выбора было видно на устройстве. Аллокатор SDK, кадровые/DMA-буферы и
карта компоновки от этого не меняются.

## Изменение лимитов PicoCalc / Lyra

`config/memory/boards/picocalc_lyra.h` задаёт длину ввода shell, буфер вставки,
историю, количество программ/процессов, квоты стека/рабочей памяти и очереди
событий. Остальные поля можно переопределить присваиванием члену `RuntimeProfile`.
`config/memory/platforms/rk3506.h` задаёт слоты кооперативного планировщика
и границы стека задачи; `config/memory/chips/rk3506g2.h` — бюджеты кучи и пула стеков.

Размеры стека, кучи и рабочих областей задаются в байтах; очереди, процессы
и история — числом элементов. Кольцо ввода оставляет один байт свободным,
поэтому `injectedInputBytes` должен быть больше `maxLineLength`.
Проверка при компиляции отвергает противоречивые профили, а планировщик
RK3506 проверяет размер стека перед созданием задачи.

Кооперативный профиль RK3506 описывает 96 КиБ стеков, 256 КиБ кучи C++
и восемь слотов задач (один — начальный/idle). FreeRTOS Lyra выделяет
стеки и арены из `heap_4` (`LEXXOS_RK3506_FREERTOS_HEAP_KIB`, обычно
512 КиБ), не используя кооперативный пул. Складывать их как свободную
физическую память нельзя. `maxProcesses` не увеличивает автоматически
число слотов планировщика. Перед повышением лимитов измеряйте свободную
память, её минимум и остатки стеков. Нулевая квота рабочей области
не резервирует буфер каждой программе. Внешняя память требует реальной
реализации аллокатора, а не только ненулевой квоты.

## Диагностика на устройстве

`mem` показывает текущую свободную кучу и её минимальный остаток, если
планировщик предоставляет статистику. `mem profile` печатает разрешённые
при компиляции лимиты ядра, стеков, shell/истории/вставки, рабочих областей,
событий, VFS и реестра устройств. Команда доступна и без статистики кучи.

`mem profile` не измеряет текущее потребление. Нулевая ёмкость кучи или
пула стеков при аллокаторе стороннего SDK означает, что профиль LexxOS
ими не управляет. Перед увеличением лимитов используйте `tasks` для
остатков стеков и `mem` для текущей кучи.

## Сборка и проверка

```sh
cmake --preset picocalc-lyra-debug
cmake --build --preset picocalc-lyra-debug
cmake --preset full-host_native
cmake --build --preset full-host_native
ctest --test-dir build/full-host_native -R 'lexxos_(memory_profile|runtime_profile_definition|sdk_memory|contract|system_contract)' --output-on-failure
```

## Измеренные остатки стеков RK3506 / PicoCalc Lyra (04.11.2026)

[Рабочий профиль и результаты](boards/picocalc_lyra_m.md#аппаратные-результаты):
`cp` — стек 8192 / свободно 3896 Б, `write` — 4096/712 Б,
`append` — 4096/552 Б, `cat` — 4096/480 Б. Все операции завершились успешно,
но последние три имеют небольшой запас. Ошибочные пути и другая
конфигурация компилятора требуют повторного измерения. Буфер `cp`
1024 Б выделяется в `ProgramMemoryArena`; рост файла не увеличивает стек.
